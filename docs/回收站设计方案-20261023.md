# 全站回收站设计方案（2026-10-23）

> **实施状态（2026-10-23）**：`restoredAt` 协议、删除快照、`/trash` 页面、恢复动作、删除文案均已落盘；
> `pb_setup/collections.json` 的 Schema 已改但**尚未导入测试站/正式站**，恢复写入前必须先升级。
> 全量 vitest 待补跑（新增同步/数据层/页面测试已绿）。

> 背景：`docs/审计报告-前端残留-20261023.md` F-1 发现笔记删除弹窗承诺了不存在的「回收站」。
> 现在改为真正实现回收站；本方案**取代**修复计划里的 D1「只改文案」。
>
> 先说结论：**这不是加一个页面那么简单**。当前同步层把「软删」定义为不可逆终态，
> 恢复必须先给同步协议加一个**显式恢复例外**，否则恢复后会被另一端的墓碑再次删掉。
>
> 另外，删除时会把跨模块关联**清空**（不是只删父记录），所以「恢复后重建关联」不能靠事后猜，
> 必须在删除时就把被清掉的链接记成**删除快照**，恢复时按快照回填。

## 一、现状约束（决定了方案长什么样）

| 事实 | 位置 | 对回收站的影响 |
|---|---|---|
| 业务删除一律软删：`deleted=1`，不搬行 | `src/repositories/repository.ts:77-90` | 数据还在，具备回收站基础 |
| 墓碑 30 天后物理清理 | `src/sync/pocketbaseAdapter.ts:715-740`、`pb_setup/pb_hooks/main.pb.js:53-65` | 回收站保质期最多约 30 天（本地离线时可能更久） |
| **墓碑不可逆**：推送侧拒绝复活、拉取侧本地墓碑只进不出 | `pocketbaseAdapter.ts:261-272`、`mergeRemote.ts:159-191` | 直接改 `deleted=0` 恢复会被再次删掉，必须新增恢复协议 |
| 删除会级联解绑/软删子记录 | `deleteCustomerCascade` / `deleteProjectCascade` / `deleteTodoCascade` / `deleteHabitCascade` / `deleteNoteFolderCascade` / `deleteTodoListCascade` | 恢复父项不等于恢复关联；链接已被清空，**事后无法凭现有数据反推** |
| 查询默认过滤 `deleted` | `src/queries/hooks.ts:18-39`、`repository.ts:33-41` | 需要单独的「已删列表」读取入口 |
| `storage.list` 包含墓碑 | `src/storage/types.ts` | 回收站可以经 StorageAdapter 读取，不直连 Dexie |

**结论**：回收站需要同时做四件事：数据读取/展示、**删除快照**、恢复动作、同步层的显式恢复协议。

## 二、两条路线

| | A. 原地恢复（同 id，新增 `restoredAt`）**推荐** | B. 克隆恢复（新 id） |
|---|---|---|
| 同步协议 | 增加「显式恢复优先于旧墓碑」的例外 | 完全不动墓碑语义 |
| Schema | 14 个集合加 `restoredAt` 字段 + 服务端升级 | 无 |
| 恢复后 id | 不变，深链/引用仍有效 | 变成新 id，深链失效 |
| 跨模块关联 | 删除时把被解绑的链接写成快照，恢复时按快照重建；目标已删的链接跳过并报告 | 全部丢失，且需要重映射，实际更复杂 |
| 多端一致性 | 需要严格测试（本方案给出判定矩阵） | 新记录天然会同步 |
| 风险 | **高**（动的是全仓最敏感的删除协议） | 中（数据会重复、关系丢失） |
| 工作量 | L（约 5–7 天，含快照与双端验证） | M（约 3–4 天） |
| 适用 | 想要「真正的回收站」 | 只想把数据找回来、可接受新 id |

**建议选 A**：回收站的核心价值是「恢复原来的那条数据」，B 会让客户/项目/待办恢复后变成另一个 id，关联和深链都断，长期看会制造更多问题。

## 三、A 方案设计

### 3.1 数据模型：`restoredAt`

在 `SyncMeta` 增加可选字段：

```ts
/** 最近一次「显式恢复」的时间；删除时清空。用于给墓碑不可逆开一个受控例外 */
restoredAt?: number
```

语义：

- **粘性**：一旦设置，后续普通编辑保留它，不因编辑而丢失。
- **只在删除时清空**：`softDelete` / 各 cascade 删除必须 `restoredAt: undefined`。
- **不是删除时间**：删除时间仍看 `updatedAt`（软删时会盖章）。
- **本地/服务端都要有**：服务端集合没有该字段时，PocketBase 会丢字段或拒绝写入，所以必须同步 Schema。

#### 3.1.1 删除快照 `trashSnapshot`

删除父项时，级联函数会清掉其他记录上的关联。为了恢复时能重建，删除动作必须在**清空前**把链接写进根墓碑：

```ts
interface TrashSnapshot {
  /** 被级联软删的子记录（只记删除时仍存活的） */
  children: { table: TrashTable; id: string }[]
  /** 被解除的弱关联（只记删除时目标仍存活的） */
  links: {
    table: TrashTable
    id: string
    field: string
    /** append：数组字段补回一个 id；set：单值字段回填；relation：补回关系对象 */
    mode: 'append' | 'set' | 'relation'
    value: string | CustomerRelation
  }[]
}
```

- 存在**根墓碑自己身上**（JSON 字段），随墓碑一起同步，所以换设备恢复也能拿到同一份快照。
- 成功恢复后清空；再次删除时重新生成，不会拿旧快照回填。
- 历史墓碑（本功能上线前删除的）没有快照：只能恢复记录本身和仍保留外键的子记录，**无法重建已清空的链接**。
- 快照只记 id/字段/关系对象，不复制整条业务数据；量级可控，但大客户（上千条流水）会到几十 KB，PB 的 JSON 字段可承接。

各父项的采集点：

| 父项 | 子记录（随父恢复） | 被清空的链接（按快照回填） |
|---|---|---|
| 客户 | `interactions` | `transactions.customerIds` 追加；`todos.customerId` / `projects.customerId` 回填；其他客户 `relations` 补回关系对象 |
| 项目 | `projectMilestones` | `transactions.projectIds` 追加；`todos/notes/interactions.projectId` 回填 |
| 待办 | — | `transactions.todoIds` 追加 |
| 笔记文件夹 | — | `notes.folderId` 回填（只记删除时仍存活的笔记） |
| 待办清单 | — | `todos.listId` 回填（只记删除时仍存活的待办） |
| 流水 | `attachments` | — |
| 习惯 | `habitLogs` | — |

### 3.2 同步判定矩阵（核心）

记 `T = updatedAt`、`R = restoredAt`、墓碑 = `deleted=1`。

| 本地 | 远端 | 判定 |
|---|---|---|
| 活 | 活 | 原 LWW（`T` 新者胜），不变 |
| 墓碑 | 墓碑 | 墓碑胜，保持删除 |
| 墓碑 | 活 + `R > 本地 T` | **恢复**：写远端活记录，`deleted=0` |
| 墓碑 | 活 + 无 `R` 或 `R <= 本地 T` | 删除胜，保持墓碑（原有语义） |
| 活 + `R > 远端 T` | 墓碑 | **恢复优先**：本地保持活，不回写墓碑 |
| 活 + 无 `R` 或 `R <= 远端 T` | 墓碑 | 删除胜（原有语义） |

推送侧（`pbUpsert`）同理：

- 远端是墓碑、本地是活记录：
  - 仅当 `本地 R > 远端 T` 才允许 PATCH 成 `deleted=0`；
  - 否则维持原「拒绝复活 + 本地镜像删除」。
- 远端是活、本地是活：原 LWW 不变。
- 本地是墓碑：原删除推送不变。

> 关键：**没有 `restoredAt` 的记录，行为与现在完全一致**。旧测试「墓碑只进不出」继续有效；
> 只有显式恢复过的记录才获得例外。

### 3.3 写入规则

- `repository.softDelete`：`deleted=1`、`updatedAt=now`、`rev+1`、**`restoredAt: undefined`**、入队 `delete`。
- 各 cascade 删除（8 处）同样清 `restoredAt`，并在**清除链接之前**构建 `trashSnapshot`，随根墓碑一次写入。
- `trashSnapshot` 只收「删除当时仍存活」的子项与链接；更早单独删除的记录不纳入，避免恢复时误复活。
- `repository.put` 遇到 `prev.deleted === 1`：视为显式复活，`restoredAt = now`、`deleted=0`、入队 `upsert`。
  - 这同时修掉一个潜在问题：`checkinHabit` 对已软删打卡的「原地复活」此前推不上去。
- `repository.put/update` 对活记录：保留 `prev.restoredAt`（表单只提交部分字段时不能丢标记）。
- `pbUpsert` 查询远端时多取 `restoredAt`；本地缺省而远端有值时，取两者较大值作为粘性标记，避免普通编辑把服务端恢复标记抹掉。
- `mergeRemote` 的 LWW 分支也保留 `Math.max(local.R, remote.R)`；墓碑分支清空 `R`。

### 3.4 恢复动作（按删除快照重建）

新增 `src/repositories/trash.ts`：

```ts
listTrash(): Promise<TrashItem[]>
restoreTrashRecord(table, id, opts?: { withChildren?: boolean }): Promise<{
  restored: number
  rebuiltLinks: number
  skippedLinks: number
  prunedRefs: number
}>
```

`restoreTrashRecord` 单事务完成：

1. 校验表在允许清单内；记录存在且 `deleted=1`，否则报可操作错误（不静默成功）。
2. 若恢复的是子记录（沟通日志/打卡/里程碑/附件），校验父记录已存活；否则提示「请先恢复所属客户/习惯/项目/流水」。
3. 若是父记录且 `withChildren`：按根墓碑的 `trashSnapshot.children` 精确恢复当时被级联软删的子记录。
   - 不再按外键扫描全部已删子项 —— 快照只收「删除当时仍存活」的子项，不会把更早单独删除的记录一起复活。
4. 按 `trashSnapshot.links` 重建被清空的关联：
   - 数组字段（`transactions.customerIds/todoIds/projectIds`）追加 id；
   - 单值字段（`todos.customerId/projectId/listId`、`notes.folderId/projectId`、`projects.customerId`）回填 id；
   - `customers.relations` 补回原关系对象（按 targetId 去重）。
   - 每条链接只写**目标仍存活**的记录；目标已被删/已清理则跳过并计入 `skippedLinks`。
5. 对根记录/子记录本身再跑一次失效弱引用清理（`pruneDeadRefs`）：指向不存在/已删实体的 id 剔除；计数 `prunedRefs`。
6. 每条 `deleted=0`、`updatedAt=now`、`restoredAt=now`、`rev+1`、入队 `upsert`；根记录清空 `trashSnapshot`。
7. 提交后 `storage.requestSync()`；返回 `{restored, rebuiltLinks, skippedLinks, prunedRefs}` 供 UI 转述。

**重建边界**：

- **本功能上线后发生的删除**：链接被完整记录，恢复时按快照重建。
- **历史墓碑（上线前删除）**：没有 `trashSnapshot`，只能恢复记录本身；仍保留外键的子记录可单独恢复，已清空的链接无法反推。
- 快照里的目标若在恢复时已经被删/被清理：跳过该条链接并明确提示「N 条关联因目标仍在回收站/已清理，未恢复」。不会为了重建链接把无关记录复活。
- 恢复后再删除：生成新快照，不沿用旧快照。
- 链接重建不改变目标记录的业务字段（只补 id / 关系对象），并把目标记录正常入队同步。

### 3.5 回收站页面

- 路由：`/trash`，懒加载 `TrashPage`；加入侧栏底部「功能配置 / 系统设置」同一区块；移动端在「个人主页 → 设置与更多」补入口。
- 顶部：类型筛选（全部/客户/流水/待办/笔记/项目/习惯/其他）+ 搜索。
- 列表：
  - 父项按类型分组，显示标题、类型、删除时间、剩余保留天数、「恢复」。
  - 子项（沟通日志/打卡/里程碑/附件）默认折叠在父项下，显示「含 N 条」；父项恢复时可选择一并恢复。
  - 独立删除的子项（父项仍存活）单独展示。
  - 父项已删而子项单独出现时，恢复按钮禁用并提示「请先恢复所属 X」。
- 恢复确认：有子项/关联时弹出确认，写明「将恢复 N 条子记录、重建 M 条关联」；无子项直接恢复。
- 空状态 + 保留期说明：「已启用同步时，删除记录保留 30 天后自动清理；本地模式不自动清理」。
- 不提供「彻底删除 / 清空回收站」（v1）：物理清理由 30 天 cron 负责，避免多端墓碑未收敛时手工删除造成幽灵记录。

### 3.6 范围

| 类型 | 是否进回收站 | 恢复方式 |
|---|---|---|
| 客户 / 沟通日志 | 是 | 恢复客户 + 快照中的沟通日志；回填流水/待办/项目关联 + 客户关系 |
| 流水 / 附件 | 是 | 恢复流水 + 快照中的附件 |
| 账本 | 是 | 单条恢复（有流水时原本就禁止删除） |
| 待办 / 清单 | 是 | 待办恢复回填流水关联；清单恢复回填当时仍存活的待办 |
| 笔记 / 文件夹 | 是 | 笔记单条恢复；文件夹恢复回填当时仍存活的笔记 |
| 项目 / 里程碑 | 是 | 恢复项目 + 快照中的里程碑；回填流水/待办/笔记/沟通关联 |
| 习惯 / 打卡 | 是 | 恢复习惯 + 快照中的打卡 |
| 客户分组 | 是 | 单条恢复（分组是规则视图，不绑客户） |
| 快速便签 / 奖杯 / 模块配置 / 工作区 | 否 | 当前无删除入口，不纳入 |

- `SecurityTab` 的「清空本地缓存」仍不可撤销，保持不变。

## 四、Schema 与部署

- `pb_setup/collections.json`：给以下 **14 个集合**加 `restoredAt`（number，可选）：
  `customers`、`interactions`、`ledgers`、`transactions`、`todos`、`todoLists`、`notes`、`noteFolders`、`projects`、`projectMilestones`、`habits`、`habitLogs`、`attachments`、`customerGroups`。
- 再给 **7 个父级集合**加 `trashSnapshot`（json，可选）：
  `customers`、`projects`、`todos`、`noteFolders`、`todoLists`、`transactions`、`habits`。
- Dexie **不需要升版本**：两个字段都不是索引字段，属于记录内普通字段。
- `remoteNormalize` 的 `JSON_FIELDS_BY_TABLE` 要把 `trashSnapshot` 加进上述 7 张表（远端可能返回 JSON 字符串，需要解析）。
- `pb_hooks/main.pb.js` 不需要改：`deleted=0` 时它已经会把 `tombstonePushed` 清零；`restoredAt` / `trashSnapshot` 只是业务字段。
- 部署顺序：**先导入 Schema，再发前端**。否则恢复时的 PATCH 可能因未知字段失败。
- 校验：`npm run check:schema`；线上升级后 `node scripts/check-schema.mjs --prod`。
- 保留期不变：30 天；不延长墓碑保留，避免服务端膨胀。
- 快照体积：只存 id/字段/关系对象，不复制正文；大客户删除时可能到几十 KB，仍在 PB 单条 JSON 字段可承受范围。

## 六、测试计划（重点）

### 6.1 同步矩阵（必须有）

1. 本地墓碑 T=100，远端活 R=200 → 本地恢复。
2. 本地墓碑 T=100，远端活 R=50 → 保持删除。
3. 本地墓碑 T=100，远端活无 R → 保持删除（旧语义）。
4. 本地活 R=200，远端墓碑 T=100 → 保持活。
5. 本地活 R=50，远端墓碑 T=100 → 删除。
6. 两端活：LWW 不变。
7. 推送：远端墓碑 T=100，本地活 R=200 → PATCH 成功。
8. 推送：远端墓碑 T=300，本地活 R=200 → 拒绝并镜像删除。
9. 恢复后再次删除：`R` 清空，另一端旧副本不能复活。
10. 普通编辑不丢 `R`（粘性）：本地 R=200 编辑后推送到远端仍带 R。

### 6.2 数据层

- `softDelete` 清 R；`put` 在墓碑上设置 R；cascade 删除清 R。
- cascade 快照：客户删除记下 interactions + 流水/待办/项目/relations；项目删除记下 milestones + 流水/待办/笔记/沟通；待办删除记下流水；文件夹/清单删除记下当时存活的笔记/待办；流水/习惯删除记下附件/打卡。
- `restoreTrashRecord`：不存在/未删 → 可操作错误；子项父项已删 → 错误；按快照恢复子项 → 条数正确；links 回填（数组追加/单值回填/relations 去重）；目标已删 → skippedLinks 计数；prune 计数正确；每条入队 upsert；根快照清空。
- 历史墓碑无快照：只恢复根记录，不误扫全部已删子项。
- `cleanupTombstones` 不碰 `deleted=0` 的恢复记录。

### 6.3 页面

- 墓碑才出现；活记录不出现。
- 父子分组、独立子项、父项已删时禁用子项恢复。
- 恢复后条目消失、toast、刷新后仍活。
- 390px 不横向溢出。

### 6.4 双端手工验收

1. A 删除笔记 → B 同步后消失。
2. A 恢复 → B 同步后回来。
3. B 离线编辑期间 A 删除 → B 推送被拒并落删；A 再恢复 → B 同步后回来。
4. A 恢复后 B 删除 → A 同步后再次消失（删除晚于恢复）。
5. 恢复客户连带沟通日志，并回填流水/待办/项目关联；恢复项目回填流水/待办/笔记/沟通；恢复文件夹/清单回填当时存活的笔记/待办。
6. 跨设备：A 删除客户（写入快照）→ B 同步到墓碑；A 在 B 上恢复 → 链接按快照重建；目标已删的链接跳过并提示。

## 七、风险与边界

| 风险 | 处理 |
|---|---|
| **时钟偏差**：恢复与墓碑比较依赖本机 `updatedAt` | 与现有 LWW 同一已知限制；恢复动作基于「较新的本机时间」，极端偏差下可能被另一端覆盖，可再次恢复。文档写明 |
| 旧客户端不认识 `restoredAt` | PB PATCH 是部分更新，旧客户端不传该字段不会清掉；但旧客户端本地可能丢标记，下一次拉取会补回。上线前建议所有设备刷新一次 |
| 历史墓碑没有 `trashSnapshot` | 上线前删除的记录只能恢复本身；仍保留外键的子记录可单独恢复，已清空的链接无法反推。UI 明确提示 |
| 快照里的目标在恢复前又被删除 | 跳过该条链接，计入 `skippedLinks` 并提示；不为了重建链接把无关记录复活 |
| 快照体积 | 只存 id/字段/关系对象；大客户可能几十 KB，PB JSON 字段可承接。若后续量级失控，再迁到独立快照集合 |
| 30 天后墓碑被物理清理 | 回收站保留期按 30 天展示；离线超过 30 天仍有本地墓碑时可恢复，但不承诺 |
| 误恢复导致数据重复 | 同 id 恢复不会新建记录；重复点恢复第二次会因「不是墓碑」被拒绝 |
| 改坏删除语义 | 所有例外都要求 `restoredAt`；无 R 的旧路径行为不变，原回归锁保留 |
