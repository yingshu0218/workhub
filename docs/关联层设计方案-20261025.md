## 1. 目标与非目标（Phase 1）

**目标**：links 表地基落地——本地 schema、服务端集合、同步登记、repository 复合函数、级联/恢复联动钩子、测试锁。部署后可同步、可级联，但**零消费方**（UI 与 Agent 工具面一律不动）。

**非目标**：不迁任何旧字段；不改任何 UI；不加 Agent 工具；不做集合层；不动事件总线；不动 `mergeRemote`（relations 并集特例等 Phase 2 退役）。

## 2. 数据模型

### 2.1 类型（`src/db/types.ts`）

```ts
/** 可作为 link 端点的表（Phase 2 各迁移项落地时按方向约定实际使用；三期集合成员可再扩） */
export type LinkEndpointTable =
  | 'customers' | 'interactions' | 'ledgers' | 'transactions'
  | 'todos' | 'todoLists' | 'notes' | 'noteFolders'
  | 'projects' | 'projectMilestones' | 'habits' | 'habitLogs' | 'attachments'

export const LINK_KINDS = ['related', 'mention', 'relation', 'attachment'] as const
export type LinkKind = (typeof LINK_KINDS)[number]

export interface Link extends SyncMeta {
  id: string        // 确定性，见 2.2
  fromType: LinkEndpointTable
  fromId: string
  toType: LinkEndpointTable
  toId: string
  kind: LinkKind
  /** kind 专属载荷（见 2.3）；json 字段，同步登记见 §3 */
  meta?: Record<string, unknown>
  createdAt: number
}
```

### 2.2 确定性 id 与幂等

```
id = `lk-` + sha256ToBase36_15(seed)
seed = `${fromType}:${fromId}|${toType}:${toId}|${kind}|${disc}`
```

- `disc`（区分同端点同 kind 的多条语义）：
  - `related` / `attachment` / `mention`：`''`（同端点对同 kind 只有一条）
  - `relation`：`${label}#${category ?? ''}`（同对客户可有多条不同语义关系，Issue #39 口径）
- **为什么确定性**：双端离线各建同一关联 → 算出同一 id → LWW 直接合流，不产生重复记录；「重复建联」天然幂等（对同 id put = 覆盖盖章）。先例：`habitLogId(habitId, date)`（`repositories/index.ts:87`）、`sha256ToBase36_15(localId)`（`remoteNormalize.ts:193`，HTTP 非安全上下文可用）。
- seed 用 `|` 分隔：端点 id 本身可含 `:`（`newId` 产物），hash 输入不解析、无歧义。
- **重命名 relation 的 label = 删除旧 link + 建立新 link**（disc 变了就是另一条关系）。语义本就如此，同步上两个操作各自传播，无中间态。

### 2.3 kind 词表 v1 与方向约定

方向约定：**from = 主动方/容器，to = 被指向方**。

| kind | from → to | meta | 迁入期 |
|---|---|---|---|
| `related` | 流水 → 客户/待办/项目（未来可扩任意原子对） | — | P2 |
| `mention` | 笔记 → customer/todo/ledger/project | `{ label }` | P2 |
| `relation` | 客户A → 客户B（对称，canonical 见下） | `{ label, category? }` | P2 |
| `attachment` | 宿主(transaction) → attachment | — | P2 试点 |

- **对称关系的 canonical 规则**：`relation` 建立前按两端 id 字典序排序再定 from/to——任一端、任一设备发起都得到同一条记录。方向信息本就无业务含义（今日 `customer.relations` 是双侧镜像），links 化后镜像双写消失。
- mention 的 `label` 放 meta、**不参与 id**：同一笔记对同一目标只一条（`extractMentions` 现状即去重），label 随 LWW 取最新。
- mentions 数组的**顺序不保留**：渲染高亮来自运行时 markdown 正则（`notes/shared.tsx`），mentions 数组今日仅用于反查与摘要，顺序无消费方。若未来需要排序，加 `meta.sortKey`，不动 id。

### 2.4 索引

```
Dexie v14:  links: 'id, kind, updatedAt, [fromType+fromId], [toType+toId]'
服务端:      idx_links_from (fromType, fromId) · idx_links_to (toType, toId)
            idx_links_updatedAt (updatedAt) · unique localId（照抄既有模板）
```

读写 links 的新 API 一律走复合索引，**禁止全表内存过滤**——这是本次改造的动机之一（现状 mentions/数组关联全是全表扫），Phase 2 读侧切换时用形状锁兜住。

## 4. repositories 设计（新文件 `src/repositories/links.ts`）

底层直接复用 `createRepository<Link>('links')`——盖章、入队、墓碑、`restoredAt` 复活凭证全部白得（`repository.ts:43-107`）。上层复合函数：

```ts
buildLinkId(from, to, kind, disc?): string                          // 纯函数
linkAtoms({ from, to, kind, meta? }): Promise<string>               // 建联：校验两端存在且未删（幽灵纪律③）→ 同 id put（幂等）
unlinkAtoms({ from, to, kind, disc? }): Promise<void>               // 解绑：softDelete 该确定性 id
linksOf(table, id, kind?): Promise<Link[]>                          // from 方向索引查询，过滤墓碑
linksTo(table, id, kind?): Promise<Link[]>                          // to 方向索引查询，过滤墓碑
cascadeSoftDeleteLinks(tx, endpoint, now): Promise<string[]>        // 级联钩子：软删指向该端点的全部 link，返回 link id 清单
reviveCascadeLinks(tx, linkIds, now): Promise<{ revived: number; skipped: number }>  // 依据快照 cascadeLinkIds 精确复活（as-built，R2）
```

裁决与口径：

- **`unlinkAtoms` 对不存在的 id 幂等静默**（不动库、不入队）——与 `softDelete` 现行幽灵防护口径一致（`repository.ts:91` 是「幂等 return」而非抛错）；重复解绑是安全终态。
- **`linkAtoms` 前置校验两端存在且未删**，否则抛可操作错误——建联产生悬挂引用是幽灵纪律③的正面违例。Phase 2 迁移回填遇到已删端点应**跳过**（迁移脚本自行判活，不走 linkAtoms 的报错路径）。
- 事务纪律照旧：以上写函数全部 `storage.transaction(['links', 'syncQueue'], ...)`；**Phase 1 不发事件**（无消费方，发孤儿事件违背现状治理方向）。
- Phase 1 **不重构** 5 个既有 cascade（`deleteCustomerCascade` 等），只给每个 cascade **追加** `cascadeSoftDeleteLinks` 一步（additive：旧字段解绑逻辑原样保留，Phase 2 迁移完成后再逐个退役）。links 软删必须与实体软删**同一事务**。
- `restoreTrashRecord` 追加 `reviveCascadeLinks`（**as-built 修正**：依据根墓碑快照的 `cascadeLinkIds` 精确复活，而非端点扫描 —— 用户在实体删除前手动解绑的 link 同样是墓碑，只有快照 id 能区分「级联牺牲品」与「用户本意」）；永久删除（purge）**刻意不连带物理删 link 墓碑**：links 不进回收站 UI（不可见、不可独立恢复），墓碑由 `cleanupTombstones` 按 30 天保留期统一清理（保留期正是其它设备拉到墓碑的窗口），反之会扩大 purge「先推后删」顺序硬约束的风险面、收益为零。

## 5. 回收站交互（裁决）

- **links 不进 TRASH_TABLES、不进回收站 UI**：它不是用户创建的独立对象，是「关联事实」。用户心智是「恢复这个客户」，其关联应连带恢复，而不是让用户在回收站里逐条恢复关联。
- **删除**：实体 cascade 事务内软删指向它的全部 links（随实体墓碑一起推送，跨设备自动传播）。
- **恢复**：`restoreTrashRecord` 恢复实体后，同事务复活其 links——**对端仍存活才复活；对端已删/已被永久删除则跳过并计数**（不为恢复关联而复活无关实体，与回收站方案「目标已删的链接跳过并报告」同口径）。
- **恢复凭证零新机制**：link 软删走既有 `deleted`+`deletedAt` 墓碑、复活走既有 `restoredAt` 协议（`SyncMeta`，`types.ts:9-38`）。
- 迁移期并存说明：Phase 2 各迁移项完成前，`TrashSnapshot.links`（append/set/relation/mention 四种 mode）继续为旧字段服务；某实体旧字段退役后，其关联的删除/恢复即完全由 links 记录承担，快照里对应链接类型自然消失。

## 6. 同步语义

- **每条 link 独立 LWW**：多端并发建不同关联 → 不同 id，各自合流；并发建同一关联 → 同 id，后写胜（等效幂等）。**结构性消灭**「数组字段整体替换互相覆盖」问题——Phase 2 退役 `mergeRemote` 的 relations 并集合并特例（`mergeRemote.ts:124`）与 transactions 数组的同类风险。
- **老客户端兼容**：旧版客户端代码里没有 `links` 这个 SYNC_TABLES 项，既不拉也不推，服务端新集合对它不可见——**升级顺序无硬约束**（建议照惯例先服务端导入、再发前端）。
- push/pull 细节零新增逻辑：幂等 upsert（localId 判存）、推送侧 LWW、删除优先、墓碑 cron，全部由既有引擎按 SYNC_TABLES 遍历自动覆盖（`pocketbaseAdapter.ts:547/696/747`）。

## 8. Phase 2-4 概要（开工前另出细化设计）

## 9. 测试锁清单

**A. `src/repositories/__tests__/links.test.ts`（R1）**
- id 确定性：同输入恒同 id；disc 参与哈希（relation 同对客户不同 label → 两个 id）
- 幂等：同 link 重复 `linkAtoms` 不产生第二条（count == 1，rev 递增）
- 幽灵纪律：`linkAtoms` 端点不存在/已软删 → 抛可操作错误；`unlinkAtoms` 对不存在 id 幂等静默且不入队
- `linksOf/linksTo`：走索引、过滤墓碑、kind 过滤；relation 的 canonical 排序（A→B 与 B→A 建出同一条）
- 写路径：put/update 均经 `storage.transaction` 且 `tx.enqueue`（writeThroughStorage 白名单保持为空即自动兜住）

**B. `src/repositories/__tests__/linksCascade.test.ts`（R2）**
- 删客户（cascade）→ 指向它的 links 同事务变墓碑（cascade 返回后立查已 deleted，且 trashSnapshot 不受影响）
- 恢复客户 → 其 links 复活；对端已删 → 跳过且计数正确
- 永久删除 → link 墓碑不随 purge 物理删（交 30 天 cleanupTombstones；as-built 裁决见 §4）——断言「purge 后 link 墓碑仍在且 deleted=1」
- 变异校验两方向（见 §7 R2）

**C. 既有锁自动纳管**：`collectionName.parity.test.ts` / `mergeNotesJsonRevive.test.ts`（links.meta ↔ collections.json type=json）。
