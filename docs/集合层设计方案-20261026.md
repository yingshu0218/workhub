## 1. 背景与现状盘点

「集合层」= 把实体归入容器的三类结构。现状是**三张特化表 + 三个成员字段**，同一语义三份实现：

| 容器 | 表 | 结构 | 成员字段 | 成员语义 | 主要消费面 |
|---|---|---|---|---|---|
| 待办清单 | `todoLists` | `{ id, name, sortOrder, createdAt }` | `Todo.listId?` | 至多一个；缺省 = 收集箱（不落库的口径） | TodoPage 左栏、`todo_*` 工具投影 |
| 笔记文件夹 | `noteFolders` | `{ id, name, createdAt }`（**无 sortOrder**） | `Note.folderId?` | 至多一个；未归类 = 缺省 | NotesPage 左栏、`listNoteFolders`/`note_createFolder` |
| 客户分组 | `customerGroups` | `{ id, name, kind?: 'manual'\|'rule', includeTags, excludeTags, rules?, sortOrder, createdAt }` | `Customer.groupId`（仅 manual） | manual = 手动单选；**rule = 标签动态圈人，无存储成员** | CrmPage 分组导航、拖拽入组 |

**现状痛点**（关联层二期同款，成员关系没有 link 化前无解）：
- **双端竞态是行级覆盖**：两端各自把待办移进不同清单，LWW 整行覆盖 → 一端的移动静默丢失。
  （二期 transactions.customerIds 迁 links 前的同型问题。）
- **删除容器的成员处理各自为政**：清单/文件夹删除怎么处置成员（解绑 or 拒绝），三处三口径。
- **成员无级联/恢复联动**：客户软删后 manual 组成员关系留在字段上（靠各读侧过滤兜底）。

## 2. 裁决点（一次列全，请逐项拍板）

### 裁决 A：通用 `collections` 表，还是保留三张特化表？

| 选项 | 内容 | 代价 | 收益 |
|---|---|---|---|
| **A1 通用表** | 新表 `collections { id, name, kind, sortOrder, config(json), createdAt }`，三张特化表迁入后退役 | 最大：三模块左栏/树/分组导航全动；rule 组的标签配置成异形 json 载荷；noteFolders 要补 sortOrder；迁移族最大 | 集合 CRUD 单一实现；新增集合类型零成本 |
| **A2 保留特化表（推荐）** | 三张表不动，**只把「成员关系」迁 links**（`kind='member'`）；容器本身保持各自 CRUD | 中：写路径收口 + 读侧索引化（二期四族迁移的同款模式，UI 左栏不动） | 双端成员变更按 per-link 合流；删除即解绑/恢复即回填全部白得；rule 组零改动 |
| A3 维持现状 | 不动 | 零 | 无；上列痛点继续存在 |

**推荐 A2**：一期/二期已验证的收益模式（per-link LWW、级联/恢复联动）恰是成员关系最缺的；
通用表的增量收益（统一 CRUD）在 2 人团队规模下有限，却要三模块 UI 全量重写——收益/风险比不成立。
A2 也不堵死 A1：将来要统一容器表时，link 化的成员关系原样带走。

### 裁决 B：成员关系 = `link kind='member'`？

- `member` 进 `LINK_KINDS` 词表；`from` = 成员实体（todo / note / customer），`to` = 容器。
- `LinkEndpointTable` 扩 `'todoLists' | 'noteFolders' | 'customerGroups'`（一期登记时**刻意排除**的三表，此为其预留位）。
- **单选语义的表达**：三类成员都是「至多一个容器」。link 模型天然多对多，单选靠**写路径选择集 diff**
  （`syncMemberLinks(tx, entityId, wantedContainerId | undefined, now)` —— 与二期 `syncRelatedLinks`
  完全同型：新容器 link 建立、旧容器 link 墓碑化，同事务）。**不做**数据库层唯一约束（Dexie 无、PB 无），
  幽灵/双挂由读侧「取 updatedAt 最新的一条」兜底（与 `Customer.groupId` 双写期的兜底同思路）。
- 备选：不建 `member` kind、字段不动（= A3），或 member 用「反向」方向（from=容器）。**不推荐反向**：
  端点校验、级联清扫、画布投影全部按「from=主动方」设计，反向要改语义。

### 裁决 C：三种特化语义如何映射（A2 口径下）

| 语义 | 映射 | 说明 |
|---|---|---|
| 待办进清单 | `todo --member--> todoLists` | 收集箱 = **无 link**（listId 缺省口径原样保留，不为「收集箱」建记录） |
| 笔记进文件夹 | `note --member--> noteFolders` | 未归类 = 无 link |
| 客户进手动组 | `customer --member--> customerGroups`（仅 kind='manual'） | 拖拽入组 = syncMemberLinks |
| 客户进规则组 | **不迁、保持视图** | rule 组成员是 `matchGroup(tags)` 的**投影**，没有存储成员可 link 化；强行迁 = 给动态视图造静态副本，口径立刻漂移 |

### 裁决 D：迁移路径

沿用二期已验证的全套模式，零新发明：
- `MIGRATED_LINK_TABLES` 扩三族（todo.listId / note.folderId / customer.groupId）；
- Dexie **v16** upgrade 一次性翻 link（确定性 id、端点已删跳过、旧键就地清）；
- pull 侧 `mergeRemote` MIGRATED 流程复用（留快照 → 派生 link 盖 `updatedAt:0/rev:0` 不入队 → 剥旧键）；
- 服务端旧列**永久保留**（老客户端降级通道 + pull 派生数据源），**服务端 schema 零变更**
  （links 集合一期已在线）。

## 3. 推荐方案（A2+B+C+D）数据模型与登记清单

拍板通过后按此登记（**全部是既有登记位的扩展，无新登记类别**）：

1. `src/db/types.ts`：`LINK_KINDS` + `'member'`；`LinkEndpointTable` + 三表。
2. `src/db/db.ts`：v16 upgrade（三族翻 link）；**不动** v11~v15 历史块。
3. `src/db/types.ts` 旧字段：`Todo.listId` / `Note.folderId` / `Customer.groupId` **类型删除**（同二期
   customerIds/mentions 的做法，防新代码继续写字段）。
4. `src/sync/`：`SYNC_TABLES` 不变（三表已在）；`MIGRATED_LINK_TABLES` + 三族；
   `JSON_FIELDS_BY_TABLE` 不变（成员字段非 json）。
5. `src/repositories/links.ts`：`syncMemberLinks`（选择集 diff，单成员特化：wanted 为
   `string | undefined`）；级联钩子 `cascadeSoftDeleteLinks` 端点自然覆盖（三表进 LinkEndpointTable 即可）。
6. 写路径收口：`saveTodo`/`saveNote`/`saveCustomer` 增容器选择参数（同 `saveTransactionWithAttachments(…, related?)` 模式）。
7. 读侧索引：`useMemberIndex`（或并入既有 `useTxnLinkIndex` 模式的 hooks 家族）。
8. 容器删除级联：`deleteTodoListCascade` 已有——迁移后**成员处置口径统一为「解绑（member link 墓碑化）+ 快照留档」**；
   `noteFolders` / `customerGroups` 若无 cascade 则补（对齐 `deleteLedgerCascade` 先例，含守卫裁决）。
9. Agent 工具面：**不新增工具**（成员变更走既有 save 路径随参数传入）；`todo_createTodo.listId`
   等投影不变。listLinks 的 read 域自动覆盖 member（登记 `TOOL_DOMAIN` 时注意 link 域白名单是否要放开 member kind——**默认不放开**，与 mention/attachment 同理由：随保存流程托管）。

## 4. 分期与成本（拍板后启动）

| 期 | 内容 | 预估 |

| R1 地基 | 登记扩展 + `syncMemberLinks` + v16 upgrade（三族一次）+ 测试锁 | 1 轮 |
| R2 迁移 | 三模块写路径收口 + 读侧索引化 + 容器删除级联对齐 | 1-2 轮 |
| R3 收口 | pull 派生验证（双端实测）+ 旧字段消费面清零确认 + 文档 | 0.5 轮（可并入 R2 尾） |

**UI 触面**：TodoPage/NotesPage/CrmPage 左栏**渲染不动**（只换数据源 hook）；
表单里「选择容器」控件不动（保存参数多传一层）。比二期（图谱/时间轴/统计全换索引）小。

## 5. 测试锁计划（对齐二期标准）

- `links.test.ts` 扩：member 确定性 id / 单选 diff（换组 = 旧墓碑新建新）/ 幽灵容器抛错。
- 级联锁：删清单 → 成员 link 墓碑化 + 快照 `cascadeLinkIds`；恢复 → 两端存活才复活。
- 双端合流锁：两端各把同一待办移入不同清单 → 合流后各持一条 member link、读侧取最新（**这条锁
  定的就是本方案的核心卖点**，等价于二期「per-link LWW 取代并集特例」）。
- 防漂移：`writeThroughStorage` / parity / alignment 既有锁自动纳管，无需新写。

## 6. 明确不做（防好心办坏事）

- ❌ rule 组不做成员存储化（动态视图造静态副本 = 口径漂移源头）。
- ❌ 不为「收集箱 / 未归类」建容器记录（缺省口径保留，建记录 = 每条历史数据都要补 link）。
- ❌ 服务端旧列不清、`collections.json` 不改（老客户端还在写；pull 派生要读）。
- ❌ 工具面不开放 `member` kind 的 `link_link` 直写（与保存流程 diff 同步打架，同 mention/attachment 裁决）。
- ❌ 拍板前不动 `db.ts` / `types.ts`。
