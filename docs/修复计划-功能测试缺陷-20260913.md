## 2. D1 · #100【P0】同步集合名不一致

### 根因

`src/sync/pocketbaseAdapter.ts` 把 **Dexie 表名直接拼进 PB 集合 URL**，而服务端有唯一一处命名不一致：

```
前端 SYNC_TABLES（:29-48）      服务端 collections.json
  ...
  moduleConfigs            ←→    module_configs   ✗ 不一致（全库唯一一处）
  customerGroups           ←→    customerGroups   ✓
  projectMilestones        ←→    projectMilestones ✓
```

实测：19 个服务端集合里 17 个与前端一一对应（`sync_state` 是有意不同步的服务端表），**只有这一处对不上**。

### 证据

- 线上页面每次同步产生 **4 条 404**：`GET /api/collections/moduleConfigs/records?page=1&perPage=200`
- 前端代码里 `moduleConfigs` 出现在 5 处 URL 拼接点（`:293`、`:337`、`:352`、`:409`，以及 `:371/:379` 的物理删除路径）

### 影响

1. **健康分配置的跨设备同步等同失效** —— 健康分权重/档位/黑名单开关在多端不一致
2. 每次同步都产生 404 噪音，掩盖真实错误
3. 配置页文案「配置随同步多端一致」目前是**假的**
4. 这条与 D3 会互相放大：配置既读不对（D3）又同步不了（D1）

### 修复方案（推荐 A）

**方案 A —— 加显式映射表（推荐）**

在 `pocketbaseAdapter.ts` 的 `SYNC_TABLES` 之后新增：

```ts
/**
 * Dexie 表名 → PocketBase 集合名。
 * 历史遗留：服务端该集合早期建为下划线命名（module_configs），前端表名为驼峰。
 * 契约由 pb_setup/collections.json 单源定义，本表只在两者不一致时列明差异。
 */
const PB_COLLECTION_NAME: Partial<Record<SyncTable, string>> = {
  moduleConfigs: 'module_configs',
}
const pbCollection = (table: string) => PB_COLLECTION_NAME[table as SyncTable] ?? table
```

然后把 5 处 `` `/api/collections/${table}/records` `` 全部改为 `` `/api/collections/${pbCollection(table)}/records` ``。

- **不动服务端**：无需迁移数据、无需重新导入 collections
- **不动本地库**：Dexie 表名与索引不变，无用户库迁移
- **单点收敛**：与既有 `assertLinks` / `buildToolsList` 同一思路 —— 消灭「多处各写一遍」的漂移面

**方案 B（不推荐）**：改服务端集合名为 `moduleConfigs` —— 需迁移数据 + 改 `collections.json` + 重新导入 + 更新部署脚本，风险与收益不成正比。

**方案 C（不推荐）**：改前端表名为 `module_configs` —— 要改 Dexie schema 并做已有用户库迁移，代价最大。

### 验证

1. 本地：`navigator` 无关，直接看同步日志 —— 不再出现 `moduleConfigs` 404，改为 `module_configs` 200
2. 线上：DevTools Network 过滤 `module_configs` → 200；`moduleConfigs` → 无请求
3. 端到端：设备 A 改健康分权重 → 设备 B 拉取后一致（这条同时是 D3 的验收前提）
4. 待处理：`syncQueue` 中可能积压的历史 `moduleConfigs` 条目 —— 修复后会自动推送成功；若上报「未知的同步表」需同步放过映射

### 防复发

在 `src/agent/__tests__/` 同层加一条 schema 一致性测试（或放 `src/sync/__tests__/`）：

```
断言 SYNC_TABLES 的每一项经 pbCollection() 映射后，
都能在 pb_setup/collections.json 的 name 列表中找到
```

这样后续任一端改名都会在 CI 被挡住 —— 和 `skill.parity.test.ts` 锁 schema 漂移是同一手法。

## 3. D2 · #192/#193【P1】Service Worker 自动注册永不执行

### 根因

`src/main.tsx:48-54`：

```js
if (import.meta.env.PROD && 'serviceWorker' in navigator) {
  window.addEventListener('load', () => {
    navigator.serviceWorker.register('/sw.js').catch(...)
  })
}
```

代码挂在 React `useEffect` 里，而**监听的 `load` 事件早已触发完毕**。

### 证据（时序探针实测，非推断）

```
   130ms  start             readyState=loading
   166ms  DOMContentLoaded  readyState=interactive
   166ms  load              readyState=complete     ← load 在此触发
   202ms  addLoadListener   readyState=complete     ← 监听器到这里才挂上
```

同时：
- 手动 `register('/sw.js')` → **立即成功** `{ok:true, scope:'https://dev.fpigeon.fun/'}`
- 干净 profile 首次访问 → `getRegistrations()` 返回 **0 个**
- 线上 `sw.js` 资源本身正常：HTTP 200、`Content-Type: text/javascript`、2524 字节

**结论：SW 本体与部署都没问题，是注册时机逻辑失效。**

### 影响

1. **PWA 离线能力完全没生效** —— 断网打不开首页（即 #193，与之互为印证）
2. 每次访问都重新拉取全部静态资源（无 SW 缓存），首屏更慢
3. 「部署后自动接管新版本」（#194）永远不会发生 —— 用户可能长期用着旧版本

### 修复方案

```js
if (import.meta.env.PROD && 'serviceWorker' in navigator) {
  const register = () =>
    navigator.serviceWorker.register('/sw.js').catch((err) => {
      console.warn('[pwa] Service Worker 注册失败', err)
    })
  // 不必等 load：SW 注册不依赖资源加载完成；且 useEffect 执行时 load 可能已过
  if (document.readyState === 'complete') register()
  else window.addEventListener('load', register, { once: true })
}
```

（更简：直接 `register()` —— 但保留 readyState 分支可兼容老浏览器行为。）

### 验证

1. **必须用干净 profile**（已有 SW 注册的 profile 无法复现首次访问）：
   - `getRegistrations().length === 1`，`scope` 为站点根
   - `navigator.serviceWorker.controller` 在二次访问时非空
2. 断网刷新首页 → 可打开（#193 转通过）
3. 部署新 build 后重访 → SW 自动更新、`clients.claim` 生效（#194 可验）
4. 确认 `public/sw.js` 的 `CACHE = 'nexus-static-v2'` 版本号随发布 bump，避免旧缓存残留

### 备注

`sw.js` 里 API 请求走「网络优先、不落缓存」，与同步引擎的设计一致，无需改动。

## 4. D3 · #22【P1】配置页 `useState` 误用导致界面与库脱节

### 根因

`src/modules/crm/intimacy/config.ts:73-79`：

```ts
export function useIntimacyConfig(): ModuleConfigIntimacy {
  const rec = useQuery(async () => await db.moduleConfigs.get(INTIMACY_CONFIG_ID), [])
  if (!rec || rec.deleted) return DEFAULT_INTIMACY_CONFIG   // ← 首帧返回默认值
  return mergeIntimacyPayload(rec.payload)
}
```

`src/modules/moduleConfig/CrmIntimacyConfig.tsx:29-30`：

```tsx
const cfg = useIntimacyConfig()
const [weights, setWeights] = useState(cfg.algorithm.weights)      // ← 首帧拿到 DEFAULT
const [thresholds, setThresholds] = useState(cfg.algorithm.thresholds)
```

**`useState` 的初值只在首次渲染生效**。首帧 `useQuery` 尚未完成 → 取到 `DEFAULT_INTIMACY_CONFIG` → 库里配置到达后 `cfg` 变了，但 `weights` 这个 state **永远不会跟着更新**。

### 证据（查库实测）

```
库内真值:  {contact:58, finance:18, todo:12, project:12}   rev=6   ← 实际生效
界面显示:  [30,30,20,20]                                            ← 恒为默认值
拖动后:    rev 5→6（有写库动作），但值未按预期更新
刷新后:    界面仍是 [30,30,20,20]，库内仍是 58/18/12/12
```

### 影响

1. 用户**无法从界面得知当前生效的权重** —— 每次进页面看到的都是默认值
2. 用户会以为「上次没保存」，反复重设；实际生效的是历次操作叠加出的怪值
3. 保存动作的归一化基准是错的（基于界面默认值而非库值）
4. **同类隐患**：`editingLevels`（`:19-26`）也用首帧 `cfg.levels` 初始化 → 自定义等级名刷新后在输入框里显示为默认名（消费端读库所以 #21 通过，但配置页自身显示是错的）

### 修复方案

把「异步数据的本地编辑态」从 `useState(初值)` 改为**脏值覆盖**模型 —— 库值始终是真源，仅在有未提交编辑时用草稿：

```tsx
const cfg = useIntimacyConfig()
// null = 无未提交编辑（直接展示库值）；非 null = 用户正在编辑
const [weightsDraft, setWeightsDraft] = useState<typeof cfg.algorithm.weights | null>(null)
const weights = weightsDraft ?? cfg.algorithm.weights
```

配套改动：

1. **滑杆 `onChange` 只写草稿**：`onChange={(e) => setWeightsDraft({ ...weights, [row.key]: Number(e.target.value) })}`
2. **提交时机不要只绑 `mouseup`** —— 现写法 `onMouseUp={() => applyWeights(weights)}` 有两个毛病：
   - 依赖闭包快照，拖动结束可能拿到旧值
   - **键盘操作（方向键）永远不触发保存**（复核时实测：方向键把 30 改成 80，但没有保存动作）
   建议改为 `onChange` 更新草稿 + `onBlur`/`onKeyUp(Enter|Tab)`/`onMouseUp` 任一提交，或加显式「保存权重」按钮
3. **保存成功后清草稿**：`await saveIntimacyConfig(...); setWeightsDraft(null)` → 自动回落到库值（此时库值已是新值，界面与库一致）
4. `thresholds`、`editingLevels` 同一模式改造
5. 提示文案保持 `'权重和≠100，已自动归一化保存'`（已有，验证其可见性即可 —— 当前是 2.6s 后 `setError('')`，自动化脚本容易捕不到）

### 验证

1. 库里设一个非默认值（如 50/20/20/10）→ 刷新配置页 → **界面显示 50/20/20/10**（修复前恒为 30/30/20/20）
2. 拖动滑杆使合计 ≠ 100 → 看到「权重和≠100，已自动归一化保存」→ 刷新后**保持归一化结果**
3. 键盘方向键调整 → 也能保存
4. 用方向键/滑杆改完后，进客户详情看健康分是否按新权重变化（端到端）
5. 多端一致需 D1 修好后才可验（D1 是 D3 的验收前提）

## 5. D4 · #32【P1】标签归一化不折叠大小写 —— 需先拍板

### 根因

`src/modules/crm/shared.ts:40-49`：

```ts
export function normalizeTags(raw: string): string[] {
  return [...new Set(
    raw.split(/[,，]/)
       .map((t) => t.trim().replace(/^#/, ''))   // ← 只做 trim + 去首 #，无大小写折叠
       .filter(Boolean),
  )]
}
```

实测：`#VIP` ✓、` VIP ` ✓ 能归一进「重点客户」组，**小写 `vip` 不能**（被当成另一个标签）。

### 存量数据实测（2026-09-13，直读线上 PB）

拍板前先把「存量迁移代价」量化 —— 结论是**此前担心的冲突在当前数据里根本不存在**：

| 数据源 | 实例数 | 归一化 key 数 | 大小写/格式冲突 |
|---|---|---|---|
| customers 标签 | 14（跨 12 个客户） | 7 | **0** |
| notes 标签 | 18 | 14 | **0** |
| todos 标签 | 15 | 10 | **0** |

- 唯一的含大小写标签是 **`VIP`**（2 处，写法完全统一）
- **零** `#` 前缀 / 首尾空格残留 → 说明输入层 `normalizeTags` 的 `trim + 去首#` 一直在生效，只有「大小写」这一维没折
- **客户分组当前 0 个存活**（测试期建的分组已删），所以「改完会不会有人突然进/出组」在现有数据上无影响面

**结论：选 A 的存量迁移代价 ≈ 0。** 原先列在「代价」栏里的存量顾虑（`VIP` 与 `vip` 并存 → 合并进组）在实测数据上不成立，这个顾虑可以划掉了。

### 待拍板：这是缺陷还是设计？

| 选项 | 含义 | 代价（按实测重估） |
|---|---|---|
| **A1. 匹配折叠、显示保留原样**（推荐） | 归组时 `VIP`/`vip`/`#VIP`/带空格 视为同一标签；客户卡片仍显示用户输入的原样 | **存量零改动**；改动面小（配组匹配 + 客户标签匹配两处改用 `tagKey`）。已知代价：标签栏可能出现 `VIP` 与 `vip` 并存（视觉像两个标签、但归组行为一致），可在配组 UI 补一句提示 |
| **A2. 存储即折叠为小写** | 输入 `VIP` 也存成 `vip`，从根上避免并存 | 显示被改写（用户输入的大写习惯丢失）；存量 `VIP`（2 处）需迁移为 `vip` |
| **B. 明确不支持小写** | 保持现状，修订用例文档 | 零代码改动，但需在 `normalizeTags` 处补注释说明，并让配组 UI 有提示 |

**推荐 A1** —— 归组行为满足用例预期，且不改变任何用户已看到的显示；存量冲突实测为 0，落地风险最低。若你更在意「标签栏不出现大小写重复」，则选 A2（代价是显示形式被规范化，且要迁移那 2 处 `VIP`）。

**若选 A**，推荐实现**匹配时折叠、显示保留原样**（不改变用户输入的显示形式）：

```ts
export const tagKey = (t: string) => t.trim().replace(/^#/, '').toLowerCase()
```

- `normalizeTags` 去重按 `tagKey` 折叠，但**保留首次出现的原样写法**
- 配组的「包含标签/排除标签」与客户标签的**匹配比较**两端都走 `tagKey`
- 存量数据：建议加一次性归一（或接受「用户下次编辑该客户时自动收敛」的渐进式）

**若选 B**，只需在 `normalizeTags` 补一行注释 + 用例文档标注，零风险。

### 验证（选 A 时）

1. 建分组含标签 `VIP` → 客户标签填 `vip` → **进组**；填 `#VIP`、` VIP ` → 进组
2. 存量：已同时存在 `VIP` 与 `vip` 的客户 → 分组人数变化符合预期（合并而非漏掉）
3. 显示端：客户卡片上仍显示用户输入的原样（`vip` 不被改成 `VIP`）

## 8. 风险与回滚

| 项 | 风险 | 回滚 |
|---|---|---|
| D1 | 映射写错会导致该集合彻底不通 | 单行常量，回滚即恢复；不影响其他 17 个集合 |

| D4 | 存量标签合并 | 选 A 前先统计存量大小写冲突数；必要时提供回退开关 |

**发布建议**：D1 + D2 + D3 可合并为一次修复提交（互相独立、风险都低）；D4 待拍板后单独提交。
