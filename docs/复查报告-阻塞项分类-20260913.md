## 七、本轮新发现的缺陷（D5，P1）

### D5 · `customerGroups` 的 `server_received_at` 配成了「仅创建盖戳」→ 分组的更新无法同步到其他设备

**证据链**：

```
① 实测现象：A 把「同步分组甲」改名为「同步分组甲（改名）」
   - 服务端查询：name = 同步分组甲（改名）   ← 推送成功了
   - B 连续两轮 reload + 各等 25s：name 仍是「同步分组甲」，rev 恒为 1  ← 拉不到

② 游标机制（src/sync/pocketbaseAdapter.ts:410-427）：
   增量拉取用 `(server_received_at > cursor || (server_received_at = cursor && id > lastId))`，
   排序也按 `server_received_at`。也就是说：**该字段不刷新 ⇒ 更新不可见**。

③ 线上实际字段配置（直查 PB）：
   customers / todos / transactions / module_configs / notes / projects →
        autodate onCreate=True  onUpdate=True     ✓
   customerGroups →
        autodate onCreate=True  onUpdate=False    ← 全库唯一一处
   （仓库 pb_setup/collections.json 里该字段明明写的是 onUpdate: true）
```

**根因**：**线上 schema 与仓库 `collections.json` 不一致**。`customerGroups` 是后加的表，导入时用的是当时的定义；后来仓库把该字段改成 `onUpdate: true`，但**没有重新导入**到线上。

**影响面**：客户分组的**改名 / 改规则 / 改排序**在跨设备场景下不会生效（创建可以）。单设备使用完全无感 —— 所以界面测试发现不了，只有双机对照才暴露。

**修复（已完成 · 2026-09-14）**：**只把线上 `customerGroups` 的 `server_received_at` 补上 `onUpdate=true`** —— 比整库重导入 `collections.json` 更精准，其余 18 个集合未受任何改动、`rules` 保持原样；原定义已备份至 `/opt/pocketbase/backups/customerGroups.schema.20260914-001841.json`。

复核证据：

1. 改一个**真实变化**的字段后，`server_received_at` 由 `15:24:15.535Z` → `16:19:30.960Z`（已刷新）
   - 插曲：第一次验证我改的是 `sortOrder: 0`（原值本来就是 0），PB 没触发更新 → 一度以为修复无效。**教训：验证「某逻辑是否被触发」时，必须改一个真实变化的字段**，否则会把「没触发」误读成「修复失败」
2. **双机端到端复测**：A 改名「D5修复后复测-6128」→ B 拉到同名（`rev=3`）→ **#38 转通过**

**同批订正**：`pb_hooks/main.pb.js` 里 `SYNC_COLLECTIONS` 的 `'moduleConfigs'` → `'module_configs'`（仓库与线上同步改，线上原文件备份 `main.pb.js.20260914-001841.bak`）。

### 附带隐患：hook 里 `moduleConfigs` 用的是驼峰名

`pb_hooks/main.pb.js` 的 `SYNC_COLLECTIONS` 列表里写的是 **`'moduleConfigs'`**，而服务端集合实际叫 **`module_configs`** —— **与 Changelog #100 修的是同一个命名不一致**。该 hook（盖 `server_received_at` / `tombstonePushed`）对这张表**实际不生效**。

目前没暴露问题，是因为 `module_configs` 的 autodate 配了 `onUpdate: true`（自动兜底）。但这意味着「双保险」只剩一层：**若哪天 autodate 再次配错，墓碑清理（`tombstonePushed`）也会跟着失效**。建议一并订正为 `module_configs`。

### 一条方法论修正（本轮踩到）

验证「UI 切换类」用例时，**别从 `documentElement` 读 CSS 变量**：主题/皮肤的变量常定义在 `[data-skin=...]` 之类的**类选择器**下，`getComputedStyle(document.documentElement)` 读不到，会误判成「变量缺失」。正确做法是读取**实际元素**的 computed style，或遍历 CSSOM 找到命中的规则后再取值。

补法照搬项目已有的两处同款实现（`/todo` 清单、`/finance` 账本）：`reorderCustomerGroups`（**同事务改记录 + 入同步队列**，否则本地顺序变了推不上服务端、换设备回旧序）+ 分组行 `draggable` 与 `⠿` 手柄。落点语义统一为「**插到目标项之前**」（因此相邻下拖一格为无变化，三处一致）。

线上实测：把第 1 个分组拖到第 3 个之前 → 库内 `sortOrder` 重排为 0/1/2 → **刷新后顺序保持**。回归锁 `reorderCustomerGroups.test.ts`（10 条）。

### 本轮的三条方法论（新增）

- **「阻塞」要分三种，处置完全不同**：① 我没做到（脚本问题）→ 改脚本；② 环境/能力上限（真 IME、真第二浏览器）→ 标人工但要**给出替代证据**（如事件级对照 + 单测）；③ **功能根本没实现** → 这是缺陷不是阻塞，该实现（#34、#158、#87 都属这一类，前两条已补）。把 ③ 混进「阻塞」会让报告低估风险面。
- **验收标准要落到「量」上，不能停在「顺不顺」**：#99「数据多了不卡」、#76/#116「清晰可读」这类主观用例，一旦换成可复现的数字（平均帧 16.4ms / 对比度 6.29:1 / 长帧 0-80），结论就从「感觉还行」变成可回归的断言 —— 这也是 D14 那 0.06 差异能被发现的原因。
- **同类控件先看项目已有范式，不要自创**：拖拽排序在 `/todo`、`/finance` 已各有一份实现（含索引修正与入队纪律），#34 直接照搬（连手柄字符都用同一个 `⠿`），三处落点语义统一为「插到目标之前」。自创第二套语义会让用户在三个列表间感到不一致。
- **无头环境里的「等待」别依赖 `requestAnimationFrame`**：隐藏/后台标签页 rAF 会被节流甚至不触发，`evaluate` 里的 rAF 循环会**永久挂起**（本轮 #99 第一版因此被 SIGTERM）。步进用 `setTimeout`、帧采样用 rAF 但整体加超时兜底。
