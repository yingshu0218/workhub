## 七、本轮新发现的缺陷（D5，P1）

### D5 · `customerGroups` 的 `server_received_at` 配成了「仅创建盖戳」→ 分组的更新无法同步到其他设备

**证据链**：

```
① 实测现象：A 把「同步分组甲」改名为「同步分组甲（改名）」
   - 服务端查询：name = 同步分组甲（改名）   ← 推送成功了
   - B 连续两轮 reload + 各等 25s：name 仍是「同步分组甲」，rev 恒为 1  ← 拉不到

② 游标机制（src/sync/pocketbaseAdapter.ts:410-427）：
   增量拉取用 `(server_received_at > cursor || (server_received_at = cursor && id > lastId))`，
   排序也按 `server_received_at`。也就是说：**该字段不刷新 ⇒ 更新不可见**。

③ 线上实际字段配置（直查 PB）：
   customers / todos / transactions / module_configs / notes / projects →
        autodate onCreate=True  onUpdate=True     ✓
   customerGroups →
        autodate onCreate=True  onUpdate=False    ← 全库唯一一处
   （仓库 pb_setup/collections.json 里该字段明明写的是 onUpdate: true）
```

**根因**：**线上 schema 与仓库 `collections.json` 不一致**。`customerGroups` 是后加的表，导入时用的是当时的定义；后来仓库把该字段改成 `onUpdate: true`，但**没有重新导入**到线上。

**影响面**：客户分组的**改名 / 改规则 / 改排序**在跨设备场景下不会生效（创建可以）。单设备使用完全无感 —— 所以界面测试发现不了，只有双机对照才暴露。

**修复（已完成 · 2026-09-14）**：**只把线上 `customerGroups` 的 `server_received_at` 补上 `onUpdate=true`** —— 比整库重导入 `collections.json` 更精准，其余 18 个集合未受任何改动、`rules` 保持原样；原定义已备份至 `/opt/pocketbase/backups/customerGroups.schema.20260914-001841.json`。

复核证据：

1. 改一个**真实变化**的字段后，`server_received_at` 由 `15:24:15.535Z` → `16:19:30.960Z`（已刷新）
   - 插曲：第一次验证我改的是 `sortOrder: 0`（原值本来就是 0），PB 没触发更新 → 一度以为修复无效。**教训：验证「某逻辑是否被触发」时，必须改一个真实变化的字段**，否则会把「没触发」误读成「修复失败」
2. **双机端到端复测**：A 改名「D5修复后复测-6128」→ B 拉到同名（`rev=3`）→ **#38 转通过**

**同批订正**：`pb_hooks/main.pb.js` 里 `SYNC_COLLECTIONS` 的 `'moduleConfigs'` → `'module_configs'`（仓库与线上同步改，线上原文件备份 `main.pb.js.20260914-001841.bak`）。

### 附带隐患：hook 里 `moduleConfigs` 用的是驼峰名

`pb_hooks/main.pb.js` 的 `SYNC_COLLECTIONS` 列表里写的是 **`'moduleConfigs'`**，而服务端集合实际叫 **`module_configs`** —— **与 Changelog #100 修的是同一个命名不一致**。该 hook（盖 `server_received_at` / `tombstonePushed`）对这张表**实际不生效**。

目前没暴露问题，是因为 `module_configs` 的 autodate 配了 `onUpdate: true`（自动兜底）。但这意味着「双保险」只剩一层：**若哪天 autodate 再次配错，墓碑清理（`tombstonePushed`）也会跟着失效**。建议一并订正为 `module_configs`。

### 一条方法论修正（本轮踩到）

验证「UI 切换类」用例时，**别从 `documentElement` 读 CSS 变量**：主题/皮肤的变量常定义在 `[data-skin=...]` 之类的**类选择器**下，`getComputedStyle(document.documentElement)` 读不到，会误判成「变量缺失」。正确做法是读取**实际元素**的 computed style，或遍历 CSSOM 找到命中的规则后再取值。

### 更要紧的是这次「差点误报」

复核过程中，我一度以为问题出在项目通用的选中态组合 `bg-primary-fixed + text-primary` 上（该组合在本仓 30+ 处使用），量到浅色 3.92:1 / 深色 3.25:1，**已经按「系统性缺陷 D15」写好登记文案**。临登记前复核了一遍测量代码，发现是**取元素错误**：

```js
row.querySelector('span')   // ← 返回的是**图标**的 span（Icon 组件外层就是 span），不是标签 span
```

`Icon` 渲染 `<span><svg/></span>` 且排在最前面，因此 `querySelector('span')` 命中图标；图标本来就是 `text-outline`，于是量出的「选中行文本 3.25:1」其实是**图标的**值。改成「取不含 `svg` 的那个 span」后，真实的标签对比度是 **6.0 / 6.12**，达标 —— **该假想缺陷已撤回、未登记**（否则会给团队凭空造出一条波及 30+ 处的「系统性缺陷」）。

由此得到本轮最值得记的一条：

- **「颜色写在子级、把父级语义盖掉」是这类问题的通用形状**：父级给状态色（选中 = primary）、子级给「次要感」色（outline），冲突时以子级为准，于是**状态的可读性被悄悄削掉**。修的时候要问一句：这条颜色表达的是「状态」还是「内容」？只有内容本身的次要感才该用 outline。
- **对比度类断言必须先确认「量到的是不是同一个元素」**：本仓的 `Icon` 会让「列表里的第一个 span」永远不是文本。定位文本节点要用「有直接文本、且不含 `svg`」这类判据，而不是 `querySelector('span')` 的顺序假设 —— 这与之前几轮踩到的「全局 first-match 点按钮」「同名记录」是同一类错误。
- **报「系统性缺陷」的门槛要比报单点缺陷更高**：说一句「这个组合在 30+ 处都不达标」等于让整个团队停下去做一次全局重构，误报的代价远高于漏报一条边界值。凡结论要落到「通用模式」上，**必须再做一次独立取证**（换一种取元素方式 / 换一个页面重现）。

- **「不测能不能，测时序」**：当一个缺陷只在特定浏览器/竞态下出现时，找一个**在另一浏览器上也会产生不同数值**的可观测量（这里是 click↔revoke 的毫秒差），比试图复现原现象可靠得多。
- **导航式 UI 的按钮不会一开始就在 DOM 里**：设置页是分区挂载的，枚举首屏按钮只看到导航与皮肤选项。两次落空后改用「先点分区导航 → 再枚举」，一次命中。这与上一轮「卡片内先枚举 button」「顶层浮层作用域取控件」是同一类教训：**先确认目标在当前 DOM 里存在，再谈点它**。

## 十六、D15 修复（2026-09-14）：黑名单三个「零消费点」开关补接线

### 缺陷形状：本会话第三次「定义了却没接线」

### 一个必须讲清的设计约束：只滤候选，不滤 `options`

`EntityLinkField.selected` 与 `MatchCombobox.selected` 都是 `options.find(o => o.id === value)` 得来的。若图省事直接把黑名单客户从 `options` 里过滤掉，**已关联的芯片/回显条会直接消失**，用户随手一保存就把关联扔了（`onChange` 只回传仍存在的 id）—— 而配置卡片自己写着「关联区始终保留，不丢数据」。

所以 `hiddenIds` 刻意**只作用于候选**（`candidates` / `matched`），`selected` 仍从完整 options 取。这条有专门的组件测试锁住两个方向相反的断言。

### 刻意**不**接的两处

- **`CrmPage.scoreInputs`**（算法兜底入参）：它是算法输入而非列表呈现，把被隐藏的客户从入参里摘掉会让算法分凭空变化（口径漂移）

### 这次复核里最有价值的两条方法论

**一、加一条「反向控制」，防的是「修过头」。**
只验「被屏蔽的看不见了」是不够的 —— 一个把客户从所有界面抹掉的实现也能过。这次的 ⑤ 明确要求**档案页直连仍然可见**：配置文案说的是「仅档案直接访问可见」，若连档案页都打不开，就是**把数据藏没了**，那比原来的缺陷更糟（用户会以为数据丢了）。凡「隐藏 / 屏蔽」类修复，都要配一条「不该被隐藏的地方仍然可见」的控制断言。

**二、对照组必须先自证「不属于被屏蔽集合」。**
第一轮复核我挑的对照客户恰好是**演示数据里本来就存在的 I7**（范伟）—— 于是「对照也没命中」，我一度读成「开关完全没生效」。实际数据完全自洽：18 活客户 − 2 位黑名单 = 16（列表计数实测 16），我只是没意识到对照组自己就该被屏蔽。
**教训：对照组不是「随便挑一个」，而必须先确认它在被测条件下应当可见**；否则一个自洽的正确结果会被读成失败，或者反向地，一个真正的失败会被对照组「恰好命中了别的条件」掩盖过去。

配套的小坑：还原断言写成了「探针客户必须没有 intimacy」，而它的原值本来就是 T3 —— 断言应当**与记录下来的原值逐字段比对**，而不是假设原值一定是空。

### P1-A · `notes` 表 json 字段未反序列化 → 笔记模块白屏

**缺陷形状：`#130` 的「只在一条分支做归一化」在另一张表上原样复发。**

`mergeRemote.ts` 的 `reviveRemoteJsonFields` 写死 `if (table !== 'customers') return` —— 即
`#130` 在 customers 上修好的「服务端 json 字段反序列化」，**其他表一律没修**。而
`pb_setup/collections.json` 的 `notes` 定义了 `tags` / `backlinks` / `mentions` 三个 json 字段。

PocketBase 的 json 字段收到字符串会当 JSON 再存一次（`types.JSONRaw.Scan`），pull 回来可能是
真数组 / JSON 字符串 / 普通字符串。落库后类型仍是 `string` 时，`NotesPage` 的
`n.tags.join(' ')`（:83）、`n.tags.slice(0,3).map`（:315）、`note.tags.map`（:499）直接抛
`TypeError` → **整页进 ErrorBoundary「模块出错了」**。**已用探针测试实测复现**（`typeof tags === 'string'`）。

修法（不再逐表写 `if`，改为**声明式字段表**）：

- 新增 `JSON_FIELDS_BY_TABLE`（`customers` / `transactions` / `todos` / `notes` /
  `customerGroups` / `moduleConfigs`）与 `JSON_ARRAY_FIELDS_BY_TABLE`（标出其中必须是数组的键，
  `intimacy` 是对象、`moduleConfigs.payload` 是任意 json，不做数组兜底）。
- `reviveRemoteJsonFields` 改为查表；数组语义字段走 `toSafeArrayField`（非数组降级单元素数组，
  保证前端 `.map` / `.join` 永不抛错），其余只做一层反序列化。

### P1-B · 笔记文件夹 3 个写入口漏 `syncEngine.requestSync()`

`modules/notes/hooks.ts` 4 个文件夹写函数里**只有 `moveNoteToFolder` 调了 `requestSync`**；
`createNoteFolder` / `renameNoteFolder` / `deleteNoteFolderCascade` 只入队不唤醒引擎。

后果不是丢失而是**延迟**：队列落库成功、30s 心跳会兜底推送，但「建完文件夹立刻关标签页」
这类操作下其他设备要等到下一次心跳才可见。对照 `todo/hooks.ts` 5/5 都调了，属本模块**回归性遗漏**；
且这 3 个函数此前**零测试覆盖** —— CI 没有拦住它，正是因为没有任何断言盯着这条纪律。

### P2-A · 两处级联删除的「读子表」在事务外（TOCTOU）

`deleteNoteFolderCascade` 与 `deleteTodoListCascade` 先在事务**外**读子行、再进事务改：

```ts
const notes = await db.notes.where('folderId').equals(id).toArray()   // ← 事务外
await db.transaction('rw', [...], async () => { ... })
```

竞态窗口内新建的子记录不会被解绑，留下**悬挂外键**（`folderId` 指向已删文件夹，
该笔记界面上既不在任何文件夹、也不进根层）。`deleteCustomerCascade` / `deleteProjectCascade` /
`deleteTodoCascade` 都在事务**内**读 —— 本处是例外。修法：读子表移入事务，并把
「含已软删子记录一并解绑」的口径与 `deleteTodoListCascade` 对齐。

### P2-B · PB 增量拉取的 filter 字符串未转义

`pbListAll` 把 `receivedAt` / `lastId` 直接内插进 filter（`server_received_at > '${receivedAt}'`），
而 `pbUpsert` / `pbDeleteRemote` 用的是 `localId.replace(/'/g, "\\'")` —— **同一件事多种写法**。
两值均服务端生成，实际可控注入面很窄，但只要将来有一处值用户可控（如按标题做服务端搜索），
就会成为真实的 filter 注入点。修法：抽出唯一入口 `escapePbFilterValue`（**先转义反斜杠再转义单引号**，
顺序错了 `\'` 会被改写成 `\\'`），全仓 filter 拼接一律走它。

### P3 · 注释与实现漂移

`mergeRemote.ts` 注释仍写「服务端 quickNotes 集合**未收录** convertedAt / convertedVia」，
而 `collections.json` 现已收录这两个字段（推送侧注释明确写着「已随 collections.json 同步升级」）。
已更正，避免误导后续维护者。
