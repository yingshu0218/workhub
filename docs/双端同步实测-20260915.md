## 4. ❌ P0：删除不会传播到第二台设备，并会演化为「删除被抹掉」

### 4.1 复现步骤（两端均真实 UI 操作）

1. B 端新建待办「双端同步验证B端建单-20260915」（id `ws-main:td:D8OsVcSH9Q`），推送成功；
2. A 端拉取到该待办——此时**两端与服务端三处都有这条记录**；
3. 在 **A 端**删除它（待办详情 → 删除 → 确认），A 端本地正确产生墓碑：
   `deleted=1, updatedAt=1789451579838`；
4. 服务端该行**直接消失**（todos 29 → 28），且全库 `deleted=1` 行数为 **0**；
5. **B 端**同步后该记录**仍然存在**：`deleted=0, updatedAt=1789451213005`（原值），UI 照常显示；
6. 在 **B 端**对该残留记录做一次普通操作（标记完成，`rev=2`），服务器上该记录以**全新 id**
   重新出现（`created` = 05:54:52Z，即 **POST 新建而非 PATCH**），`deleted=0`；
7. **A 端**拉取后，因远端 `updatedAt`(1789451691263) > 本地墓碑(1789451579838)，
   按 LWW 覆盖本地墓碑 → A 端该记录 `deleted` 回到 **0**，出现在「已完成」视图（计数 11 → 12）。

**最终状态：A 端删除的记录，在 A、B、服务器三处全部"活着"——删除被彻底抹掉。**

### 4.2 墓碑在服务端从未形成可被观测的中间态

在服务端挂 100ms 粒度只读探针，观测 `ws-main:td:D8OsVcSH9Q` 一行的生命周期：

```
   0.00s  (0, '2026-09-15 05:46:54.922Z')   ← 记录存在，deleted=0
   8.30s  ('ABSENT',)                        ← 直接消失，中间从未出现 deleted=1
```

墓碑在服务端的存在窗口 **< 100ms**。任何对端都**不可能**通过 pull 游标（按 `server_received_at` 增量）
拿到这条删除——删除因此无法传播。

### 4.3 根因

`src/sync/pocketbaseAdapter.ts` → `pushImpl()` 的 delete 分支：

```ts
if (item.op === 'delete') {
  // 墓碑记录：推送墓碑（对端 LWW 收敛）后对服务端做物理删除。
  await pbUpsert(cfg, item.table, rec)                      // ← 推墓碑（正确的半句）
  await pbDeleteRemote(cfg, item.table, rec.id as string)   // ← 紧接着物理删除（问题所在）
  await db.meta.put({ key: tombstonePushedKey(...), value: 1 })
}
```

注释写的是「推送墓碑（对端 LWW 收敛）后对服务端做物理删除」——**意图是让墓碑被对端看到**，
但两行紧邻执行，墓碑在服务端只存活毫秒级，**意图被自己的实现短路了**。

### 4.4 判定为缺陷（而非有意设计）的五条互相印证的证据

1. **服务端整套墓碑机制被短路**：`pb_setup/pb_hooks/main.pb.js:40-63` 专门在写入时盖
   `tombstonePushed=1`、并由 cron 每日 04:00 物理删除「超过保留期（30 天）的墓碑」——
   若客户端推完即删，该 cron **永远无事可做**，这套机制形同虚设。
2. **hook 自身注释自相矛盾**：既称客户端是「PATCH 墓碑 → DELETE 物理删除」两步，
   又称该标记「供服务端 cron 定向清理墓碑」——两者只能成立其一。
3. **接收端已完整实现墓碑合并**：`src/sync/mergeRemote.ts:172` 纯 LWW 放行、
   `:286` `record.deleted = remote.deleted ? 1 : 0` —— 若墓碑永不留存，**这段是死代码**。
   即接收侧已经为「墓碑可被拉到」做好了全部准备。
4. **客户端清理流程的注释与阈值都指向 30 天后删除**：同文件 `cleanupTombstones()`（609-639 行）
   写明「已确认推送的墓碑清理时对服务端做物理删除（服务端墓碑膨胀由 pb_hooks cron 兜底）」，
   阈值 `Date.now() - 30 * 24 * 60 * 60 * 1000`。物理删除**本应由清理流程在 30 天后执行**，
   而不是在推送时立刻执行。
5. **无任何测试锁定当前行为**：`src/sync/__tests__/` 仅 3 个用例，全部是 merge 纯函数
   （`collectionName.parity` / `mergeLocalEditProtection` / `mergeJsonFieldRevive`），
   **删除推送路径零覆盖**——与「缺陷能溜进来」完全吻合。

### 4.5 建议修复（最小改动）

删除 `pocketbaseAdapter.ts:509` 的 `pbDeleteRemote` 调用，delete 分支只保留
`pbUpsert`（推墓碑）+ `db.meta` 标记：

- 服务端保留墓碑行 → hook 自动盖 `server_received_at`（对端游标可拉到，**删除得以传播**）
  与 `tombstonePushed=1`（供 cron 定向清理）；
- 30 天后由**客户端 `cleanupTombstones()`** 与**服务端 cron** 双重兜底物理清除 → 不会无限膨胀；
- 需配套补一个「删除跨设备传播」回归用例（当前该路径无任何测试覆盖）。

改动量约 1 行 + 1 个用例；因接收侧与清理侧逻辑均已就绪，属于「让实现回到自身既定设计」。

## 5. 附带发现（P2，不影响上面结论）

1. **待办列表行不提供删除入口**：行内只有「专注 / 作废」，删除须进详情抽屉。
   而「作废」是**状态位**（`status='voided'`，记录保留），与「删除」（软删、不可撤销）语义不同，
   列表上并排出现易误操作。
2. **LWW 不区分「墓碑」与「活记录」的优先级**：当前纯按 `updatedAt` 新者胜。
   修复 §4.5 后，若对端在不知情期间编辑过该记录（`updatedAt` 晚于墓碑），对端编辑仍会胜出、
   记录存活。这是 LWW 的既有语义，但「删除是否应始终优先」值得作为产品口径确认一次。
   → **2026-09-15 已拍板：删除优先**（软删为不可逆终态），落地见 §8。

## 6. 结论

- **推送 / 拉取 / 双向 / 离线补传 / 新设备接入**五条主链路全部验证通过，数据零丢失、无重复。
- **删除传播**这条路是断的，且后果不是「对端少删一条」，而是**删除被反向覆盖、记录复活**——
  属于 Local-First + LWW 架构下最危险的一类不一致（split-brain）。
- 因该缺陷在**推/拉主链路上看不出来**（只有删除才暴露），建议修复前**不要再往多设备推广录入**，
  否则会产生越来越多「删不掉的僵尸记录」。

## 7. P0 修复与复验（同日收口）

### 7.1 实际根因是**两条**，不是一条

§4.5 当时估的是「删掉 `pocketbaseAdapter.ts:509` 一行 + 补一个用例」。修复时按 §4.4 的线索
把链路又走了一遍，发现**推送侧只是显性根因，接收侧还有一条同样会致死后遗症的分支**，
只改推送侧仍然会留下跨设备永久不一致：

| # | 位置 | 缺陷 | 后果 |
|---|---|---|---|
| 1 | `pocketbaseAdapter.ts` `pushImpl()` delete 分支 | 推完墓碑紧接着 `pbDeleteRemote` 物理删除 | 服务端没有墓碑可拉 → 对端**不可能**收到这条删除 |
| 2 | `mergeRemote.ts` 「本地未推送编辑保护」分支 | 该分支把 `deleted` 写回本地值（`local.deleted ?? 0`），把**更新的远端墓碑**静默吃掉 | 对端明明拉到了墓碑也不落删 → 本地滞留幽灵记录；推送侧 LWW 又会一直跳过它 → 永久不一致，直到某次编辑让它复活 |

第 2 条的触发条件比第 1 条更隐蔽：对端只要**在离线期间编辑过该记录**（队列里留着一条未推送 upsert），
收到的墓碑就会被「保护」掉，而且此后**再也不会**被拉到（游标已推过）。

### 7.2 改动清单

1. `src/sync/pocketbaseAdapter.ts` — delete 分支只保留 `pbUpsert`（写墓碑）+ `tombstonePushed` 标记，
   **移除物理删除**；注释写明「为什么不能推完就删」。
2. `src/sync/mergeRemote.ts` — 保护分支条件加 `&& !revived.deleted`：远端是墓碑时不保护。
   此处远端 `updatedAt` 必然**严格大于**本地（上方 172 行 LWW 已短路），
   即「删除发生在本次编辑之后」——按 LWW 归删除胜，与 §5.2 的「删除/编辑优先级」策略是两件事。
3. `pb_setup/pb_hooks/main.pb.js` — 修掉自相矛盾的注释（原文既称客户端「PATCH 墓碑 → DELETE 物理删除」
   又称该标记「供 cron 定向清理墓碑」），并把 cron 标注为**服务端墓碑的唯一常规出口**。
   服务端 hooks 无功能改动，测试机上已核验 `md5` 与仓库一致（`4dea265a…`），cron 在线。

### 7.3 回归用例（离线，随 `npm test` 常跑）

新增 `src/sync/__tests__/deleteTombstonePropagation.test.ts`（5 例），覆盖原来零覆盖的删除推送路径：

| 用例 | 钉住的不变式 |
|---|---|
| delete 只写墓碑，绝不物理删除服务端行 | 整轮推送**没有任何 DELETE**；墓碑 PATCH 的 `deleted=1`；标记照常盖章 |

**用例有效性经反向验证**：把两处修复各自临时回退，对应用例**确实转红**

## 8. 「删除优先」定案与落地（2026-09-15，同日第二轮）

### 8.1 口径：软删是**不可逆终态**

§5.2 留的产品口径，用户当日拍板：**删除优先**。语义收紧为 —— 任一端为墓碑即墓碑胜，
**不再比较 `updatedAt`**；任何更晚的编辑都不允许让记录复活。

定案依据（不是拍脑袋，是先核过代码事实）：

1. 全仓 `deleted: 0` 只出现在**新建**处（`db/seed.ts` 的 `meta()`、`repositories/index.ts` 的
   新建路径、`db/types.ts` 的默认值），**不存在**「把墓碑改回 `deleted=0`」的路径；
2. 界面上**没有「撤销删除 / 回收站 / 恢复」入口**（全仓搜 `撤销/恢复/restore` 命中的都是
   会话快照恢复、存档导入这类无关路径）；
3. 待办的「恢复」是 `status='voided'` → 未完成，**属状态位语义**，与软删（`deleted`）是两套东西
   （`docs` 与 `types.ts:138/157` 已写明「作废保留记录可恢复，区别于软删」）。

三者合起来：把删除设为不可逆**不会破坏任何现有流程**，且是唯一能让「已删记录不再复活」成立的收口方式。

### 8.2 落地：**三处收口**，少一处仍会跨设备永久不一致

| # | 位置 | 收口 | 不做的后果 |
|---|---|---|---|
| 1 | `mergeRemote.ts` `mergeRemoteRecord()` | 墓碑判定**提前到 LWW 短路之前**：本地墓碑 → 只进不出（`skip`）；远端墓碑 → 强制落删，`updatedAt` 抬到两者较大值 | 「本地编辑更晚」会把远端墓碑挡回去；而 pullImpl 游标随即推过该位置 → 这条删除**再也拉不到** |
| 2 | `pocketbaseAdapter.ts` `pbUpsert()` | 远端 `deleted=1` 而本地非墓碑 → **拒绝复活**（不发 PATCH/POST），并把 `deleted` 加进同一次判存查询的 `fields`（**零额外请求**） | 对端更晚的编辑会以 PATCH 把服务端墓碑覆盖成 `deleted=0`，删除自此无从收敛 |
| 3 | `pocketbaseAdapter.ts` `pushImpl()` | 拒绝复活后**就地镜像**：把本地也落成墓碑 + 盖 `tombstonePushed` 标记 | **只跳过推送是不够的**：该墓碑的 `server_received_at` 早已被本表游标推过，pull 不会重拉 → 本端永远停在 `deleted=0` 的幽灵态，每次编辑都重演一次被拒 |

另放宽一处判定：`pushImpl` 里「按墓碑推送」的条件从「队列 `op === 'delete'`」改为
「**或**记录此刻已是墓碑」—— 收口 1 会把对端墓碑落到本端，而队列里可能还留着该记录更早的
`upsert` 条目；若只认 `op`，这条墓碑会走 upsert 路径上行（结果虽同为 `deleted=1`，但**漏盖标记**，
于是逃过 `cleanupTombstones()` 的本地清理）。

### 8.3 为什么**推送侧**非设防不可（本轮最容易漏的一点）

同步引擎是**先推后拉**：`engine.runSync()` 先 `adapter.push(pending)` 再 `adapter.pull(cursor)`。
而编辑走 **2s 去抖**、拉取走 **30s 心跳** —— 对端「不知情期间」的编辑**几乎总是先被推上来**，
这一推就会把服务端墓碑覆盖成 `deleted=0`。**只做接收侧（收口 1）挡不住这条时序**，
这是「只改 mergeRemote 就够了」这个直觉判断的反例。

### 8.4 遗留项建议：pull 落库的墓碑如何清理（P2，**待拍板**）

**问题**（PR #6 评审①）：`cleanupTombstones()` 只清带 `tombstonePushed` 标记的墓碑；
pull 落库的墓碑**不经过推送**、自然没有标记 → 永不被清理。§7 修复后每次远端删除都会在对端生成一条。

先把这类墓碑分两类，处置不同：

- **甲类：本端曾持有该记录，对端删了** → 墓碑是**必要状态**（本地必须显示为已删）；
- **乙类：本端从未持有**（`local === undefined`）→ 纯幽灵，只占存储。

**建议按性价比做前两条，第三条明确不做：**

| 方案 | 做法 | 评估 |
|---|---|---|
| **A（推荐，先做）** | `cleanupTombstones()` 的保留条件从「有 `tombstonePushed` 标记」放宽为「**有标记，或队列中仍有该记录的待推送条目**」 | 约 5 行。语义正确：墓碑一旦「本端已收敛（队列无待推送条目）」就只是垃圾 —— 删除只经服务端传播，设备间不直连，故本地墓碑并不承担「再传给第三台设备」的职责。30 天 cutoff **保持不变**，不会立刻清掉新墓碑。**时序上也安全**：对端删除 vs 本端编辑同时存在时，队列里的 upsert 要先经收口 3 出队，墓碑才满足清理条件 |
| **B（可选增量）** | `mergeRemote` 远端墓碑分支加 `if (!local) return 'skip'` —— **不为从未持有的记录写墓碑**，直接消灭乙类 | 彻底但改变的是「落库策略」而非「清理策略」，建议**单独提交**并加用例钉住「skip 后本端不会凭空出现幽灵记录」。风险点已核：pull 按 `server_received_at` 升序，不会出现「tombsone 先到、live 后到」 |
| **C（不做）** | 把条件放宽成「是墓碑就清」 | 会把「delete 尚未送达服务端」的墓碑也清掉 —— 正是 #114 之前的丢删除路径（v0 为此设过 P0-1 竞态防护），**明确不做** |

**当前实际影响评估（供排期参考）**：墓碑单条约 200–400 B，且本端删除后 30 天会被正常清理；
新增的只是「对端删除」这一路（每次一条）。按每日几十次删除估，一年量级 <10 MB，
**不影响 UI（读取侧已过滤 `deleted`）**。故结论是：**A 值得尽快做（成本极低），但不阻塞任何事**。
