## 1. 四个命令的分工

| 命令 | 作用 | 何时跑 |
|---|---|---|
| `npm test` | 全量用例（`vitest run`，跑完退出） | 每次交付前**必跑** |
| `npm run lint` | `eslint src` | 每次交付前**必跑** |
| `npm run build` | `check:icons` + `tsc -b` + `vite build` | 交付前必跑（`tsc` 单跑：`npx tsc -b`） |
| `npx vitest run <path>` | 只跑某个文件/目录 | 开发中反复验单点时用 |

**交付前的最低组合**：`npx tsc -b` && `npm run lint` && `npm test` && `npm run build` —— 四绿才算完。

## 3. 环境与隔离（写测试时必读）

- **默认 `environment: 'node'`**（`vitest.config.ts`）：纯数据/纯函数用例不带 DOM 开销。
  组件用例在**文件头**加 `// @vitest-environment jsdom` **按文件**切换。
- **IndexedDB 用 `fake-indexeddb`**：`import 'fake-indexeddb/auto'` 后 Dexie 即可用，
  通常配 `beforeEach(() => Promise.all(db.tables.map(t => t.clear())))` 保证用例隔离。
- **不要 `vi.mock` 掉被测对象**：本仓刻意保持 `vi.mock` 0 处 —— 用例跑**真实生产函数**
  （假 IndexedDB、真 Dexie、真 repositories），避免「测了 mock 没测生产路径」。
  需要隔离外部副作用时用 `vi.spyOn(console)` / `spyOn(URL.createObjectURL)` 这类环境桩。
- **源码扫描型锁**：本仓有一批「读源码做断言」的防漂移锁（见下），它们**不执行被测代码**，
  而是防止「约定被悄悄改掉」。写这类锁时**务必加反向校验**（喂一段已知错误形状 → 断言能识别），
  否则判据本身写错会一路绿灯（本仓踩过这个坑）。

## 5. 常见误判（本仓真实踩过）

1. **「全量红」先看是不是 flaky**：源码扫描类用例会遍历整个 `src` 树；
   若在用例内**每个 `it` 各读一遍**，全量并发时 I/O 争用会拖过 5s 超时 → 假红。
   **修法**：遍历结果在**模块作用域只读一次**。（`download.test.ts` 已如此修，见 C-5）
2. **改了实现却「测试照旧全绿」**：先怀疑判据没生效 —— 做**变异校验**
   （手工改坏一处 → 确认锁报红 → 恢复）。本仓曾出现「`perl` 正则没匹配上，测试照绿」的假绿。
3. **`npm run build` 突然失败于删除保护**：在本机沙箱里，vite 清空 `dist/` 可能触发
   **批量删除保护**（`SAFE_DELETE_BULK_CONFIRM_REQUIRED`）—— 这**不是代码问题**，沙箱豁免下重跑即可。
