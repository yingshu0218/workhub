## 一、#44【P1】笔记 · 中文输入法不误触 —— ✅ 已通过

### 结果

2026-09-14 由操作者用**简体拼音 + 真实键盘**验证通过：在 @ 提及浮层的筛选框里打拼音、候选字未确认时按 `Enter`，**正文未被插入任何提及、浮层未被关闭、输入法正常选字**，选完字后筛选继续按已确认的中文工作。

代码侧的配套（让这条以后不容易被改坏）：组合态守卫已收口到 `src/shared/ime.ts` 的 `isImeComposing`（`isComposing` 或 `keyCode === 229`），原 5 处内联实现全部改走它；`src/shared/__tests__/ime.guard.test.ts` 7 条锁定，含**源码扫描**禁止再出现内联判据。

### 这条在测什么

中文/日文输入法在**候选字还没确认**的阶段按 `Enter`，语义是「选字」，不是「确认/提交」。如果应用把这一下 `Enter` 当成业务快捷键，就会出现：**拼音还没上屏，就把 @ 提及提交掉了**、或者**把浮层关掉了** —— 真实打字时高频遇到，但无头浏览器驱动不了系统候选窗，所以只能人工验。

具体要验的是「笔记页 @ 提及浮层的**筛选输入框**」上的这一下 `Enter`。对应代码在 `src/modules/notes/NoteEditorPage.tsx` 的浮层 `onKeyDown`，判据已收口到 `src/shared/ime.ts` 的 `isImeComposing`（`isComposing` 或 `keyCode === 229`）。

### 前置

- macOS + 实体键盘，输入法切到**简体拼音**（或日文罗马字）
- 浏览器 Chrome 或 Safari 均可（两种都试更好）

### 操作步骤

1. 打开站点 → 左侧「笔记」→ 任选一篇进入，点右上角**编辑**（或点「新建笔记」，新笔记会直接进编辑态）。
2. 把光标点在正文里，输入 `@`。
   → **应出现提及浮层**：上方一个「输入关键词模糊匹配…」筛选框 + 四类实体 tab + 一串候选条目。
3. **点一下那个筛选框**（让焦点在浮层里，不是在正文里）。
4. 用拼音打一个词，比如敲 `chen`（或 `he`）——**先不要按空格、也不要按回车选字**，让候选面板停在「几个候选字还没上屏」的状态。
5. 就在这个「候选未确认」的状态下，**按 `Enter`**。
6. 观察三件事（这是判据）：
   - ① 笔记正文里**没有**被插入任何 `@[某人](customer:…)` 形式的提及；
   - ② 提及浮层**没有关闭**（筛选框和候选还在）；
   - ③ 输入法自己的候选面板正常响应这次 Enter（即字被选上了，拼音变成汉字进入筛选框）。
7. 继续：等拼音变成中文后，看筛选框是否**按刚确认的中文继续正常筛选**（候选列表随之变化）。
8. 再验正向路径：此时（组合已结束）按 `↑` / `↓` 能上下移动候选，按 `Enter` 能**正常插入**该条提及到正文。
9. 顺手再试两个相邻场景（同一浮层内）：
   - 在筛选框里中文输入时按 `Space`（空格也是选字键）；
   - 组合未确认时按 `Esc`（应只关输入法候选，不应关掉整个提及浮层）。

### 判定

| 结果 | 判定 |
|---|---|
| ① ② ③ 全部成立，且第 7~9 步正常 | **通过** |
| 拼音未确认时按 Enter，正文被插入了提及 / 浮层被关掉 / 出现拼音字面文本（如正文里出现 `chen`） | **不通过**，请记录 |

### 失败时要记录的信息

- 浏览器 + 版本、输入法名称（如「简体拼音 - 全拼」）
- 菜单栏输入法状态、出问题时的截图（**能同时看到浮层、筛选框内容与输入法候选窗**）
- DevTools → Console 的报错（若有）截图
- 是「每次必现」还是「偶尔」

### 已知边界（说明，不是让你复现）

无头环境里三方尝试都失败了：CDP 的 `Input.imeSetComposition` 注入的组合态**不会让后续按键带上 `isComposing=true`**（实测 Enter 的 `isComposing` 为 false），@ 浮层也唤不起来（依赖真实光标/选区上下文）。所以这一条**只能人工**。

## 二、#98【P2】兼容与性能 · 换个浏览器再来一遍 —— ⏸ 暂缓（无手机）

### 结果

2026-09-14：当前没有 iPhone，手机端测试暂缓，**不纳入本轮结论**。

### ⚡ 精简版（不需要手机，2 分钟，建议现在就做）

macOS **自带 Safari**，它和 Chrome 是两个内核（WebKit vs Chromium），足以覆盖「换个浏览器」这一半的风险。打开 Safari 后照这 3 步：

1. **打开刷新**：访问 http://<TEST_HOST>:9001 → 确认能看到左下角速记框、侧栏「功能配置」、客户页左侧分组栏（看不到就是缓存了旧版）→ `Cmd + R` 刷新 → 页面正常、侧栏能切页、Safari 的「开发 → 显示 JavaScript 错误」窗口无红字
2. **速记**：左下角速记框打一句话 `Enter` → 出现「已记入速记 · 查看」→ 点「查看」能跳到那条笔记
3. **分组同步**：客户管理 → 新建分组（名称 + 「须包含标签」至少填一个，这是必填）→ 保存 → 切回 Chrome 刷新，看该分组是否出现（两端要在「设置 → 云端同步」连同一账号）

**手机端留待有设备时补什么**：触摸操作（拖拽排序、长按）、iOS 键盘弹出是否挡住底部输入框、iOS 版本差异（老版本 Safari 的 API 缺口）、`100vh` 在 Safari 地址栏收放时的表现。

### 这条在测什么

Chrome 之外的浏览器（Safari / iOS Safari）能否正常使用。自动化只能驱动 Chromium，本机也没有 WebKit 内核可驱动（Playwright 未安装，装 WebKit 需额外下载），Chrome 的 iPhone 视口模拟 **不等于** Safari。

### 完整步骤（有手机时按这个跑）

### 前置

- macOS 上的 **Safari**，或 **iPhone**（二选一，两者都测更好）
- 若是 iPhone：能访问 `http://<TEST_HOST>:9001`（明文 HTTP，公网可达即可），并用 `demo@nexus.local` 登录

### 要跑的三条

#### 1) 打开刷新

1. 用 Safari / iPhone 打开 http://<TEST_HOST>:9001
2. **先确认不是旧版**：能看到左下角速记输入框、侧边栏「功能配置」入口、客户页左侧分组栏、设置里的「AI Agent 桥」页签 —— **看不到就是缓存了旧版**（iPhone 上到 设置 → Safari → 清除历史记录与网站数据 再来）。
3. 按 `Cmd + R`（iPhone：下拉刷新）刷新一次
4. 观察：页面正常渲染、无白屏、无「模块出错了」；侧栏可切换页面；Console 无红色报错

**这几点在 Safari 上最值得盯**：页面高度（Safari 地址栏收放导致 `100vh` 变化，底部是否被挡）、日期/数字输入控件、弹层是否是 `position: fixed` 正确（Safari 对 `backdrop-filter` 处理不同）。

#### 2) 速记

1. 左下角「速记」输入框里打一句话，按 `Enter`
2. 期望：出现「已记入速记 · 查看」的确认提示
3. 点「查看」→ 应跳到笔记页并打开刚记的那条
4. iPhone 上额外确认：输入时键盘弹出，输入框**没有被键盘挡住**

#### 3) 新建分组同步（跨端）

1. 在 Safari / iPhone 上：客户管理 → 左下「新建分组」→ 填名称（如 `Safari验证`）+ **「须包含标签」至少填一个**（如 `重点`，这是必填，不填会拦保存）→ 保存
2. 期望：分组立即出现在左栏「我的分组」下
3. 换一台设备（或在 Chrome 里）：打开同一站点、**保持「设置 → 云端同步」连的是同一账号** → 刷新
4. 期望：`Safari验证` 这个分组在另一端也出现（同步延迟通常几秒内，最迟等一次 30s 心跳）
5. 反向再验一次更稳：在 Chrome 里新建一个分组，回 Safari 刷新看是否出现
