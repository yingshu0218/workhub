## 二、⚠️ 一处已撤销的误判：别信文档记录，信主机的 label

**2026-10-26 写这份文档时，判断是「正式站跑 `cd74317`、落后 26 提交、新 schema + 旧代码」——这个判断是错的。**

2026-10-27 上机实测：容器跑的是 **`ab0d253`（10-26）**，落后 main 只有 **5 个提交**（4 个文档 + 1 个代码）。也就是说 links / 集合层 / v16 那些**早就上线了**，「新 schema + 旧代码」的风险当时并不存在。

### 误判是怎么产生的

1. `PROGRESS.md` 的「正式环境」行停在 2026-10-21 的升级记录（`cd74317`），之后**没有人回写**；
2. 而 `.deploy-state` 只记录**测试站**的源码部署，正式站部署**没有留痕机制**；
3. 于是「文档里最新的记录」看起来像「线上最新的状态」—— 两者实际差了一次部署。

### 判据（以后只认这条）

> **判断线上跑的是什么，只认主机上 `docker image inspect` 的 revision label。**
> 文档记录、PROGRESS 状态表、`.deploy-state` 都只是「上次有人记得写」的快照，不是事实。

### 仍然成立的纪律

代码与 schema 必须**同步推进**（谁先谁后都要跟一次部署）。这不是对现状的描述，而是下次改 schema 时的顺序约束：
schema 先上线而代码跟不上（或反之），中间窗口里的读写口径会对不上。

## 三、上线流程（6 步，每步都有判据）

### 步骤 0 · 本地门禁（唯一入口）

```bash
npm run check:all        # check:icons + tsc -b + eslint + vitest --maxWorkers=4
```

**判据**：`EXIT=0`，且摘要行是 `0 failed`。⚠️ vitest **必须 4 worker**——默认并发下本仓会随机器负载假红，那不叫「重跑一次变绿」，叫环境问题。

### 步骤 1 · 推送并用 CI 门禁做验收

```bash
git push origin main
```

推送会触发两条流水线：GitHub 只读镜像同步 · **`build-web-image`（现在多了一个前置 stage `quality gate`）**。

**这一步是首次真实执行新门禁，请当成一次验收而不是日常发布。** 在 CNB 构建日志里确认：

| 观察点 | 期望 | 2026-10-27 首跑实测 |
|---|---|---|
| `quality gate` stage 通过 | `npm ci && npm run check:all`（node 22，与 Dockerfile 同版本） | ✅ 通过（镜像能产出即证明前置 stage 已过） |
| `docker build` / `docker push` | 推 `:<8位sha>` 与 `:latest` | ✅ `0da81790` 与 `latest` 均在 tags 列表 |
| 镜像 revision label | = 推送的提交 | ✅ `latest` → `0da817909f8c…`（与 HEAD 逐字相同） |
| GitHub 只读镜像 | 远端 main = 本次提交 | ✅ 两侧一致 |

**无 docker daemon 时也能核对镜像版本**（纯 HTTP，凭据取自 `cnb git-credential`）：

```bash
PW=$(printf 'protocol=https\nhost=cnb.cool\n\n' | cnb git-credential get | sed -n 's/^password=//p')
BT=$(curl -s -u "cnb:$PW" \
  "https://docker.cnb.cool/service/token?service=cnb-registry&scope=repository:blueteam0715/workhub:pull" \
  | sed -n 's/.*"token":"\([^"]*\)".*/\1/p')
curl -s -H "Authorization: Bearer $BT" https://docker.cnb.cool/v2/blueteam0715/workhub/tags/list
# label 要再看一层：manifests/latest → config.digest → blobs/<digest> → config.Labels
```

**门禁红了怎么办**（按根因分两类，处置完全不同）：

- **红在环境**（`npm ci` 网络失败、镜像里缺 git、node 版本不满足）→ 这是**门禁自身的问题**。
  立刻修 `.cnb.yml`，或临时把 `- <<: *quality-gate` 摘掉再推。
  ⚠️ **绝不能留下一个永远红的门禁** —— 那比没有门禁更糟，会训练所有人习惯性忽略红灯。
- **红在代码**（tsc/lint/test 真的挂）→ 这正是它的价值：**不要绕过**，回去修。

### 步骤 2 · 主机拉取并重启

```bash
ssh <host> 'cd /opt/workhub && sudo docker compose pull && sudo docker compose up -d'
```

**判据**（四条都要看，缺一条都不算成功）：

1. 容器 `healthy`（`docker compose ps`）
2. 日志出现「N 个集合均已存在，跳过导入（幂等）」—— 说明 schema 已在位、没有误重建
3. `docker image inspect … revision` = 你推的提交（**这是唯一可信的版本判据**）
4. `npm run check:schema -- --prod` 仍输出「完全一致」

⚠️ **部署完立刻回写台账**（本文档 §一 + `PROGRESS.md` 状态表的「正式环境」行）。
本次误判的根因就是这个动作没做：10-26 有一次部署，但没人回写，于是文档一直说「跑着 `cd74317`」。

### 步骤 3 · 入口面验收

```bash
for u in / /api/health /sw.js /manifest.webmanifest /relay/; do
  printf '%-22s %s\n' "$u" "$(curl -sS -o /dev/null -w '%{http_code}' https://team.fpigeon.fun$u)"
done
```

**判据**：五个全 `200`。

⚠️ **不要用「线上 JS 哈希 == 本地 dist 哈希」判断镜像通道的成败** —— CI 是全新 `npm ci`，依赖树/构建环境与本地不同，哈希本来就不同。镜像通道只认 **revision label + 代码特征**（比如新版本特有的工具名/文案）。

### 步骤 4 · 数据面验收（人工，见第四节）

代码上线 ≠ 能用。这一步才是「项目是否真的交付」的分界线。

### 步骤 5 · 打 tag（给这批提交一个回滚点）

自 `v1.2.1`（10-09）起已累积 **82+ 提交**，跨了三个架构级变更（links 关联层 / 集合层 member link / 事件总线泛化），**没有 tag 就没有「上一个已知好」**。

```bash
git tag -a v1.3.0 -m "v1.3.0 · 关联层原子化 + 集合层 + 事件总线泛化"
git push origin v1.3.0     # tag 会触发 release-web-image（同样过 quality gate）
```

⚠️ 两套版本号语义不同、**不要互相覆盖**：`package.json` 的 `0.1.0` 是**应用包版本**（原生壳产物名取自它，停在 0.1.0 表示 API 未稳定承诺），tag 是**项目里程碑**。

## 五、回滚

| 层面 | 怎么做 | 后果 |
|---|---|---|
| **部署前先留退路** | 主机上给当前镜像打本地 tag：`docker tag <当前image> workhub:rollback-$(date +%F)`，并记下 digest（`docker image inspect --format '{{index .RepoDigests 0}}'`） | **这一步最容易漏**。制品库 tag 会被清理，本地 tag 是最后一道保险 |
| 代码 | compose 里把 image 换成 **8 位短 sha tag**（如 `workhub:cd74317a`）→ `up -d` | 立即回到旧版本 |
| 数据 | 升级前先备份：`cp /opt/workhub/data/data.db /opt/workhub/data/data.db.bak-$(date +%F)` | 唯一能真正恢复数据的手段 |
| ⚠️ schema | **不回滚**（21 集合保持） | 旧代码跑在多出来的列上是安全的（不读即不存在），**但看不懂 v16 的 member link 归属** → 回滚后「清单/分组归属」会显示为空，**数据没丢**，再升回来即恢复 |

⚠️ **镜像 tag 是 8 位短 sha，不是 `git log` 显示的 7 位**（`git log` 默认 7 位，注册表用 `${CNB_COMMIT_SHORT}` = 8 位）。
实测：`manifests/cd74317` → **404**，`manifests/cd74317a` → 正常。要拿正确短 sha 用 `git rev-parse --short=8 <commit>`。

**回滚前必读**：先把 `data.db` 备份掉。代码可以随时换，数据卷没有第二次机会。

## 六、凭据与安全边界

**⚠️ 本文不记录任何密码/token 值，只记录它们在哪。**

| 位置 | 权限 | 内容（键名） | 是否入库 |
|---|---|---|---|
| 仓库根 `.deploy.env` | `600` | `DEPLOY_*`（测试站）、`PROD_PUBLIC_URL` / `PROD_SUPERUSER` / `PROD_SUPERUSER_PASSWORD` / `PROD_APP_USER` / `PROD_APP_PASSWORD` | ❌ gitignore |
| 主机 `/opt/workhub/.env` | `600` | `PB_SUPERUSER` / `PB_SUPERUSER_PASSWORD` / `WORKHUB_RELAY_TOKEN` | ❌ 只在服务器 |
| 本机 `~/.workhub/relay.json` | `600` | Agent 桥 token（由 `npm run agent:setup` 写入） | ❌ 本机派生 |
| 浏览器页面 | 内存 | 桥 token（设置页生成/展示） | ❌ 不落盘 |

三条硬边界（不要放宽）：

1. **正式站超管与测试站超管是两套账号**（同名不同密码）→ 用 `check:schema -- --prod`，不要手工拼密码。
2. **relay 零特权**：`relay/*.mjs` 只依赖 `node:` 内置，不 import 任何 `src/` 业务代码；数据始终留在浏览器 IndexedDB。
3. **`users` 公开注册必须保持关闭**，否则「任何登录用户可读写全部业务集合」+「任何人可自助注册」= 公网裸奔。这条不在代码里，重建空库后要手工重做（步骤见部署文档 §5.4）。

1. **主机上的制品库凭据会过期** —— `pull` 报 401 时不要去查镜像。

2. ⚠️ **容器日志里有明文 relay token**（entrypoint 启动时打印「接入 token：…」）。
   读日志需要主机权限，所以不是公网泄露面；但**截图/贴日志给别人时要打码**。
   彻底解决应改为脱敏打印（只留前 4 位）—— 属待修项，改它需要重新构建并发布镜像。
