## 二、⚠️ 当前最大的风险：代码落后于 schema

正式站现在是「**新 schema + 旧代码**」：

- schema 已经在 10-25/10-26 同步到 21 集合（含 `links`、member link 相关列）
- 但镜像代码停在 10-21，**不认识** `links` 表，也不知道 v16 的「成员关系 = link」口径
- 它仍在按旧字段写 `todos.listId` / `notes.folderId` / `customers.groupId`

**空库时零风险**。但一旦在这台机器上开始录真实数据：

- 旧代码写的归属信息，新代码上线后**读不出来**（新代码读 member link，不读行字段）→ 表现为「清单/分组里的东西突然全空了」
- 而 pull 侧的 `mergeRemote` 会把旧字段派生回 link，所以**不丢数据**，但会有一次「看起来像丢失」的惊吓

**结论（顺序不能反）**：先把新代码部署上去，再开始录数据。

## 三、上线流程（6 步，每步都有判据）

### 步骤 0 · 本地门禁（唯一入口）

```bash
npm run check:all        # check:icons + tsc -b + eslint + vitest --maxWorkers=4
```

**判据**：`EXIT=0`，且摘要行是 `0 failed`。⚠️ vitest **必须 4 worker**——默认并发下本仓会随机器负载假红，那不叫「重跑一次变绿」，叫环境问题。

### 步骤 1 · 推送并用 CI 门禁做验收

```bash
git push origin main
```

推送会触发两条流水线：GitHub 只读镜像同步 · **`build-web-image`（现在多了一个前置 stage `quality gate`）**。

**这一步是首次真实执行新门禁，请当成一次验收而不是日常发布。** 在 CNB 构建日志里确认：

| 观察点 | 期望 | 若不符 |
|---|---|---|
| `quality gate` stage 通过 | 跑的是 `npm ci && npm run check:all`（node 22，与 Dockerfile 同版本） | 见下方「门禁红了怎么办」 |
| `docker build` / `docker push` 执行 | 推 `:<short-sha>` 与 `:latest` | 门禁失败会自然阻断——这是设计，不是故障 |
| 镜像 label | `org.opencontainers.image.revision` = 你推的提交 | 用 `docker manifest inspect` 或在主机上 `docker image inspect` 核对 |

**门禁红了怎么办**（按根因分两类，处置完全不同）：

- **红在环境**（`npm ci` 网络失败、镜像里缺 git、node 版本不满足）→ 这是**门禁自身的问题**。
  立刻修 `.cnb.yml`，或临时把 `- <<: *quality-gate` 摘掉再推。
  ⚠️ **绝不能留下一个永远红的门禁** —— 那比没有门禁更糟，会训练所有人习惯性忽略红灯。
- **红在代码**（tsc/lint/test 真的挂）→ 这正是它的价值：**不要绕过**，回去修。

### 步骤 2 · 主机拉取并重启

```bash
ssh <host> 'cd /opt/workhub && sudo docker compose pull && sudo docker compose up -d'
```

**判据**（三条都要看，缺一条都不算成功）：

1. 容器 `healthy`（`docker compose ps`）
2. 日志出现「N 个集合均已存在，跳过导入（幂等）」—— 说明 schema 已在位、没有误重建
3. `npm run check:schema -- --prod` 仍输出「完全一致」

### 步骤 3 · 入口面验收

```bash
for u in / /api/health /sw.js /manifest.webmanifest /relay/; do
  printf '%-22s %s\n' "$u" "$(curl -sS -o /dev/null -w '%{http_code}' https://team.fpigeon.fun$u)"
done
```

**判据**：五个全 `200`。

⚠️ **不要用「线上 JS 哈希 == 本地 dist 哈希」判断镜像通道的成败** —— CI 是全新 `npm ci`，依赖树/构建环境与本地不同，哈希本来就不同。镜像通道只认 **revision label + 代码特征**（比如新版本特有的工具名/文案）。

### 步骤 4 · 数据面验收（人工，见第四节）

代码上线 ≠ 能用。这一步才是「项目是否真的交付」的分界线。

### 步骤 5 · 打 tag（给这批提交一个回滚点）

自 `v1.2.1`（10-09）起已累积 **82+ 提交**，跨了三个架构级变更（links 关联层 / 集合层 member link / 事件总线泛化），**没有 tag 就没有「上一个已知好」**。

```bash
git tag -a v1.3.0 -m "v1.3.0 · 关联层原子化 + 集合层 + 事件总线泛化"
git push origin v1.3.0     # tag 会触发 release-web-image（同样过 quality gate）
```

⚠️ 两套版本号语义不同、**不要互相覆盖**：`package.json` 的 `0.1.0` 是**应用包版本**（原生壳产物名取自它，停在 0.1.0 表示 API 未稳定承诺），tag 是**项目里程碑**。

## 五、回滚

| 层面 | 怎么做 | 后果 |
|---|---|---|
| 代码 | `/opt/workhub/docker-compose.yml` 把 image 换成 `workhub:<旧的short-sha>` → `up -d` | 立即回到旧版本 |
| 数据 | 升级前先备份：`cp /opt/workhub/data/data.db /opt/workhub/data/data.db.bak-$(date +%F)` | 唯一能真正恢复数据的手段 |
| ⚠️ schema | **不回滚**（21 集合保持） | 旧代码跑在多出来的列上是安全的（不读即不存在），**但看不懂 v16 的 member link 归属** → 回滚后「清单/分组归属」会显示为空，**数据没丢**，再升回来即恢复 |

**回滚前必读**：先把 `data.db` 备份掉。代码可以随时换，数据卷没有第二次机会。

## 六、凭据与安全边界

**⚠️ 本文不记录任何密码/token 值，只记录它们在哪。**

| 位置 | 权限 | 内容（键名） | 是否入库 |
|---|---|---|---|
| 仓库根 `.deploy.env` | `600` | `DEPLOY_*`（测试站）、`PROD_PUBLIC_URL` / `PROD_SUPERUSER` / `PROD_SUPERUSER_PASSWORD` / `PROD_APP_USER` / `PROD_APP_PASSWORD` | ❌ gitignore |
| 主机 `/opt/workhub/.env` | `600` | `PB_SUPERUSER` / `PB_SUPERUSER_PASSWORD` / `WORKHUB_RELAY_TOKEN` | ❌ 只在服务器 |
| 本机 `~/.workhub/relay.json` | `600` | Agent 桥 token（由 `npm run agent:setup` 写入） | ❌ 本机派生 |
| 浏览器页面 | 内存 | 桥 token（设置页生成/展示） | ❌ 不落盘 |

三条硬边界（不要放宽）：

1. **正式站超管与测试站超管是两套账号**（同名不同密码）→ 用 `check:schema -- --prod`，不要手工拼密码。
2. **relay 零特权**：`relay/*.mjs` 只依赖 `node:` 内置，不 import 任何 `src/` 业务代码；数据始终留在浏览器 IndexedDB。
3. **`users` 公开注册必须保持关闭**，否则「任何登录用户可读写全部业务集合」+「任何人可自助注册」= 公网裸奔。这条不在代码里，重建空库后要手工重做（步骤见部署文档 §5.4）。
